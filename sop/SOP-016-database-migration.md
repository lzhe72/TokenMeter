# SOP-016 数据迁移

**修订：** 1　**状态：** baselined　**适用：** all

## 目的与范围

验证本地/服务端 schema、SQLite→MySQL 或错误数据修复，并确保备份可恢复。

## 触发条件

schema、存储引擎、历史聚合或数据格式变化；发布升级涉及数据库迁移。

## 前置条件

SOP-004 明确源/目标版本、兼容和恢复策略，SOP-006 定义预期；实际执行需隔离数据库、真实迁移/备份/恢复程序。

## 输入

受支持源版本、数据生成程序、迁移脚本、独立记录数/聚合期望、数据库版本和备份目标。

## 执行步骤

1. 核对目标隔离与所有权，生成具有边界/历史数据的源库并记录 schema、记录数和聚合基线。
2. 用真实备份程序保存源状态，先在另一隔离实例验证备份可恢复。
3. 运行已实现、已登记的迁移入口，检查 schema版本、关键字段、成员隔离、唯一性、记录数及 Token/费用聚合。
4. 测试中断、重复执行和不兼容源版本；确认失败状态可被发现，恢复策略有效而非继续写入损坏库。
5. 在旧版→候选 App/服务真实链路验证升级、读写及回归；正式执行只按已验证预案进行。
6. 当前无真实数据库/迁移程序时只完成设计和数据准备，实际迁移验收 BLOCKED，不编造 Alembic/数据库命令。

## 输出

迁移/备份/恢复实现及在明确版本矩阵上的校验结果。

## 成功与失败判据

数据与独立基线一致、应用可用、失败恢复经过实际验证才通过；只检查迁移脚本退出零不能证明数据完整。

## 异常恢复

发现不一致立即停止后续写入，保留源库、失败目标和日志；用已验证备份恢复到明确状态后复测，不盲目执行逆向迁移。

## 证据位置

迁移报告、源/目标 schema、数据摘要、备份及恢复验证结果，按 run_id 归档并关联 release_id。
