# SOP-019 Git 版本追踪

**修订：** 9　**状态：** baselined　**适用：** all

## 目的与范围

由项目总控把各需求分支先集成到本地 `master`，对最终整合树执行适用门禁，再统一推送远端 `master`；保存源码、版本与本地发行的关联。安装包及原始证据不上传 Git。

## 触发条件

需求分支达到本地集成条件，或已通过正式本机发布门禁、需要建立源码 Tag。PR 只在远端策略要求时作为受控替代路径，不再是默认集成步骤。

## 前置条件

用户已授权总控自主整合、推送和适用门禁后的发行。分支具有对应 release_id、文档基线和适用检查结果；本地与远端 `master` 的实际状态可核对。产品迭代/修复在远端集成前须有固定测试程序及**本地 master 最终整合提交**对应的完整产品 E2E；正式 Tag 还须 SOP-017/018 的最终包和 PASS 通行证。仅规范及其必要文档附件的独立分支可在SOP-008结构、基线和治理检查通过后先行并入源码`master`，但不得记为产品E2E、发布PASS、通行证或Tag；后续产品候选须以这个新基线整合并完成完整门禁。2026-10-01用户再次确认 Git 仅用于源码版本管理、本机承担产品测试，旧 Actions 必需检查已按此决定移除；其余远端保护仍须真实满足。未提交的用户改动不得覆盖或带入整合。

## 输入

需求分支及其提交、版本档案与 Changelog、`origin/master`、最终整合候选 SHA/tree、适用检查、原始 E2E/包证据和通行证摘要；远端保护规则及2026-10-01迁移的前后快照、工作流触发及适用的用户决定。

## 执行步骤

1. 由总控运行 `git status --short --branch`、`git remote -v`、`git ls-remote --heads origin master`，核对当前分支、远端及未提交改动。以只读 GitHub API 核对 `master` 的 PR、required checks（名称、预期 App、strict）、管理员执行、强推/删除规则，并核对工作流实际触发条件；保存带时间的原始规则快照，不能从旧记录推断当前保护。保存各需求分支提交和 release_id；只将源码、文档、配置、测试及数据程序纳入 Git。DMG/ZIP、数据库、密钥、`node_modules`、原始报告和通行证保留本机忽略目录。
2. 每个需求分支先按其任务和既定 TC 完成适用基础检查及开发阶段回归，记录失败与阻断。总控先以 `git fetch origin master` 获取远端状态，在干净检出中执行 `git switch master`、`git merge --ff-only origin/master`；若远端与本地已分叉则停止并查明差异，不覆盖本地独有提交、用户改动或强制重置。按既定顺序逐支执行 `git merge --no-ff <需求分支>`，遇冲突按原需求/用例修正并保存整合记录。需求分支不各自推送或合并远端 `master`。
3. 最后一支整合后记录 `git rev-parse master`、`git rev-parse 'master^{tree}'`、父提交和工作树状态。产品候选对这个**实际本地 master 候选**执行 SOP-008/013/014 的适用检查与本次及此前已交付功能的完整 E2E；正式发行继续 SOP-017/018，从同一最终 DMG 安装验证。独立纯规范分支仅做SOP-000/008/024的结构、基线、治理和引用检查，明确`release_eligible=false`，不出产品通行证或Tag。分支单独 PASS、旧候选报告、PR 状态或仅 tree 相似均不能替代后续产品整合后的完整验收。任何产品整合、冲突修复、源码/依赖/包输入改变均生成新候选并重新核验。
4. 本地候选门禁完成后再次读取远端保护并核对 `origin/master` 未前进。2026-10-01远端`master`已移除三项旧 Actions required checks，仍强制 PR、管理员执行和对话解决，禁止强推/删除；以每次实际读回为准。若允许直推且全部实际要求已满足，普通快进推送并读回 SHA；当前强制 PR 则走第5步。不得把本地 PASS 冒充远端检查、强推、管理员绕过、删除保护、伪造或手写 PASS；若实际保护变化且无法满足，远端集成记为 BLOCKED，本地产品结果单独保留。
5. 对当前强制 PR 规则，以**同一已测本地 master 整合候选**建立远端 PR 来源分支，保留本地整合顺序及候选 SHA/tree；核对 PR base/head、实际保护和远端`master`未前进。PR 审查与对话解决等实际要求须满足；远端若新增 required checks，逐项核对其名称、App 来源、结论及 strict 基线，不能用本机报告或手写状态替代。GitHub Actions 完整多环境测试只在用户明确要求时设计和启动。若新保护与本机流程冲突，保存快照和影响后按 SOP-000 及明确用户决定修订；不得私自临时关闭保护再恢复。
6. 合并 PR 前复核本地原始门禁仍对应未变的候选 SHA/tree、包输入及源码；远端 base 前进或 PR 修改候选内容时，形成新本地整合候选并重跑受影响完整门禁。按保护规则合并后读回远端 `master` SHA/tree，与被测候选建立严格 tree 映射；有内容差异或无法证明一致时停止发行并重新验证。记录不同的远端合并 SHA，不能写成原被测 SHA；不要让各需求分支绕开本地整合直接在远端分别合并。
7. 正式发布仅在本机 SOP-018 PASS、通行证与本地 `master` 最终候选/原包一致且远端已读回后，创建同 release_id 的 annotated 源码 Tag，绑定被测提交或第6步已证明严格 tree 相同的远端合并提交，并核对远端 Tag；不创建 GitHub Release，不上传安装包或测试原件。首次尚未发行可继续同版本修候选，已正式发行的 Tag 不移动。
8. 在本机 `.local/git-sync/`、版本 06 和本地发行记录保存需求分支→本地合并 SHA/tree→门禁 run/package/passport→远端保护快照/决定/检查→远端 `master` SHA/Tag 的映射及实际命令、退出码；未执行的步骤只记待办，不写 PASS。

## 输出

本地 `master` 整合与门禁记录、远端 `master` 读回、必要时的源码 Tag 和可查询的本地发行索引。

## 成功与失败判据

纯规范整合成功要求范围仅含SOP及使其可执行的规范附件，SOP-008结构/基线和治理检查PASS、远端保护实际满足、远端树与已检查分支树严格对应，并记录产品`release_eligible=false`。产品集成成功另要求所有需求分支按顺序纳入最终本地候选，适用检查和产品完整 E2E 在该候选上真实 PASS。允许快进推送时远端 `master` 读回 SHA 与本地一致，强制 PR 时须有第6步的严格 tree 映射及远端提交记录。正式 Tag 另须最终包门禁和通行证 PASS。任一适用检查 FAIL/BLOCKED、无法解释的远端差异、未清理工作树、缺证据或推送拒绝均不得记完成。

## 异常恢复

保留原始失败和已发生的远端事实；不强推、改写历史、移动 Tag 或修改门禁结果。重新核对远端与本地变更，形成新的整合候选并重跑受影响的完整产品门禁；保护策略新增无法满足的要求时保持 BLOCKED，按第5步处理，不自行降低要求。

## 证据位置

本机 `.local/git-sync/`、`releases/<release_id>/06-iteration-record.md`、原始测试/门禁目录和本地发行档案。
