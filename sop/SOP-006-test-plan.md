# SOP-006 测试计划

**修订：** 3　**状态：** baselined　**适用：** all

## 目的与范围

为每个验收条件同时定义用例、测试用户/数据程序、SOP、原生 E2E 和证据要求。

## 触发条件

开始功能/修复设计，或已有行为、数据和平台支持范围改变。

## 前置条件

SOP-002–005 的需求、设计和任务明确；阅读 [测试策略](../docs/testing/strategy.md)及 [执行规范](../docs/testing/execution.md)。

## 输入

验收条件、功能矩阵、数据集登记、历史回归与缺陷、支持平台和数据库。

## 执行步骤

1. 对照独立 `tests/acceptance.json` 与需求定义表，将每条验收条件映射到正常、失败、权限及边界场景，使用稳定 E2E ID。要求“规格定义↔验收清单↔用例”双向齐全，不能通过删除必测用例缩小集合。
2. 定义本次应执行集合：目标全部场景加所有此前已交付功能；无关未来 planned 项不加入，目标不得降级状态规避。按真实能力在功能矩阵登记 `depends_on`；依赖必须已在本轮或更早版本交付，禁止早期验收依赖未来版本。跨功能场景放入依赖齐备的版本，并保留稳定追踪。
3. 定义角色、账号、日志/价格/故障数据、固定种子和参考时间，安排生成、真实账号导入、重置/清理程序。
4. 独立计算 expected，不能调用生产统计逻辑生成自身答案；明确原始日志版本与规范化样例的区别。
5. 写明 UI→真实服务/数据库的执行路径、系统交互、矩阵、命令、退出码、报告和失败处理；未实现绑定如实为 null。
6. 登记 `tests/feature_matrix.json` 与 `tests/datasets.json`，确保任务包含所有未实现程序。验收清单中的 `data_requirements` 必须由绑定数据集的 `capabilities` 覆盖；基础数据 available 不代表覆盖扩展场景。规划数据不足时记录具体缺项，进入 in_progress 前必须补齐真实绑定、可用数据和所需能力。

## 输出

04-test-plan.md、场景/数据登记、可被 Codex 执行的 SOP 合同和 E2E 实现任务。

## 成功与失败判据

本轮每条验收条件都有场景、数据、独立预期和自动执行方案；仅人工步骤、截图或 API 自测不能替代产品 E2E。

## 异常恢复

发现不可自动执行的关键系统路径，记录所缺环境或执行器并安排实现；不得省略该路径或手填通过。

## 证据位置

版本测试计划、矩阵、数据清单和具体 SOP；06-iteration-record.md 记录覆盖决定与缺口。
