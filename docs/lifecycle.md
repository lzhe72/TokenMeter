# 文档驱动的全流程框架

> 2026-10-01当前执行基线：[Electron本机设计](architecture/01-electron-local.md)。Electron/React/TypeScript、Vite/electron-vite、Playwright Electron、electron-builder；本机按功能固定TC开发回归，用户另行启动正式发布后才做最终候选跨需求完整E2E、打包及发行。当前仅macOS15 Intel实测范围。Git保存源码/文档/版本；DMG、更新包、报告和通行证只存本地，Actions仅明确多环境要求时启用。旧逐版发行流程保留在历史记录中。

这是 TokenMeter 的工作顺序。最高规则是“规范驱动文档，文档驱动设计、开发、测试、发布和迭代；每一步必须有 SOP”。先确定流程和文档合同，再基于文档实现产品，之后重复同一流程迭代。每轮由唯一 `release_id` 贯穿。[文档标准](standards/documentation.md) 定义文档合同，[SOP 总索引](../sop/README.md) 定义大模型如何执行每一步。

```text
定义 SOP 总索引及独立文件
  → 编写 SOP、规范与模板
  → 版本立项与档案建立
  → 需求定义
  → 功能点及具体开发任务列表
  → 技术设计与开发计划
  → 基于每项开发任务设计逐条测试用例、输入及预期
  → 发布预案
  → 文档基线完整性检查
  → 工程骨架准备及真实运行验证（SOP-009）
  → 数据/账号程序与真实业务失败基线（SOP-010/011）
  → 按文档实现业务功能（SOP-012）
  → 各需求独立worktree的干净WIP/候选可快进保存到远端同名功能分支（只表示代码已保存）
  → 按本功能已基线固定TC执行 / 逐步记录 / 失败修复与受影响回归
  → 总控按依赖顺序在本地 master 固定源码 SHA/tree 与真实功能状态
  → 总控可选单一远端 integration 分支镜像祖先链（不授产品PASS）
  → 全部目标源码完成后统一按保护规则登记远端 master
  → 用户另行明确正式发布时：最终原包跨需求完整E2E / 适用真实升级 / 机器门禁 / 通行证
  → 本机归档正式包并登记该正式发行Tag
  → 收集问题并建立下一轮版本需求
```

## 1. 每一阶段的输入、输出和完成条件

| 阶段 | 输入 | 必须产生的文档/产物 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| SOP 清单与定义 | 所有工程阶段和执行动作 | [SOP 清单](../sop/README.md)、每份 SOP 的输入/步骤/输出/判据/恢复 | 无未覆盖步骤，每份 SOP 可指导大模型执行 |
| 版本立项 | 已确认目标及上版结果 | release_id、manifest、当前索引、迭代记录 | 编号合法且唯一，范围和输入明确 |
| 需求定义 | 用户目标、使用场景、上版问题 | 01-requirements.md：用户、范围、权限、可验收行为、非目标 | 每条需求有稳定 ID 和可观察的验收条件，无影响架构的未决问题 |
| 功能拆解 | 已确定需求 | 02-breakdown.md：需求→功能→子任务、依赖、版本目标 | 所有需求被功能覆盖，边界和依赖明确 |
| 技术设计 | 功能拆解与当前实现 | 03 中的独立技术设计章节或单独设计附件 | 按 SOP-004 先完成设计，再安排 SOP-005 实施计划；与需求、权限和数据约束一致 |
| 开发计划 | 功能/任务与架构约束 | 03-development-plan.md：实现顺序、模块/接口/数据变化、兼容/迁移、风险、交接 | 每个任务可执行，输入输出与完成标准明确 |
| 测试计划 | 需求、功能及开发计划 | 04-test-plan.md：用例、账号/数据、生成与重置程序设计、独立预期、SOP、自动 E2E、环境矩阵 | 每条验收条件映射用例；每个场景有数据与自动执行方案 |
| 发布预案 | 本次版本范围、测试计划 | 05-release-plan.md：计划内容、发布条件、安装/部署、升级/恢复、预计证据清单；Changelog 版本条目 | 上线条件可由门禁程序判断，不能出现“测试后补” |
| 文档基线/开发切片 | 完整计划与manifest，或整版draft中不受未决项影响的明确TASK/TC | 整版baseline/质量结果，或固定ID/依赖隔离/结构与治理结果的development_slice_ready记录 | 切片只开放其009–014；整版draft、其余TC和发行仍阻断 |
| 工程骨架 | 完整文档基线与明确骨架任务 | 真实 App、服务、数据库初始化、原生测试 target/runner 及运行探针 | 真实构建、启动和探针通过后能运行业务测试；无预先业务红测/PASS 要求 |
| 数据与测试 | 基线设计与可运行骨架 | 账号/数据程序、真实场景测试和目标行为失败证据 | 数据与绑定齐全，失败来自缺失业务而非环境/编译错误 |
| 业务实现 | 完整文档基线、真实测试与失败证据 | 功能代码、同步文档和可执行测试 | 按计划实现；独立源码任务可在运行受阻时推进，实际验收仍待执行 |
| 远端功能分支检查点 | 各需求独立worktree的干净WIP/候选提交及真实检查状态 | 同名远端功能分支SHA/tree读回、`remote_code_saved`和WIP/候选状态 | 仅证明源码已保存；失败/未测原样保留，`release_eligible=false` |
| 开发功能回归 | 本功能固定候选、已基线TC、构建物和隔离环境 | 真实App逐TC/变体报告、逐步证据、独立结果Excel | 该功能全部适用TC通过才记功能PASS；FAIL/BLOCKED可保留源码整合，不冒充验收 |
| 远端源码登记 | 全部目标源码本地整合、功能回归状态已真实记录、受保护远端入口 | 保留各里程碑祖先的远端master源码与独立读回收据 | 来源SHA/tree一致；无逐版完整E2E/稳定包前置，正式Tag待办 |
| 正式发行 | 用户另行明确发布、最终候选完整门禁PASS与对应原包 | 本机正式DMG、SOP-020归档、实际发布记录和正式Tag | 提交、版本、跨需求证据、产物摘要及适用真实升级一致 |
| 产品迭代 | 用户反馈、缺陷、运行数据 | 新 release ID 和新需求档案 | 不改写历史 tag/通行证，按同一流程启动下一轮 |

文档编制中按 SOP-024 执行 `python3 scripts/check_docs.py --mode structure`，允许后序计划保持 draft 并返回原步骤。001–007 齐全后，SOP-008 才运行 `--mode baseline` 及质量检查。首个骨架按已基线设计建立；缺工具链只阻断依赖其运行结果的任务，签名/生产凭据只作最终包及发布验证前提。

上述完成条件是文档和机器检查条件，不额外引入每一步都要用户手工批准的流程。需要产品决策时明确提问；常规实现和测试由 Codex 自主完成。

## 2. 文档先行不等于预填通过结果

开发前写发布**预案**，明确要发布什么、如何验证、如何上线、如何恢复。测试与发布实际发生后，由程序生成带时间、提交、产物摘要和结果的**执行记录**，保存在本地版本目录中。

发布预案可以提前存在；PASS 通行证不能提前存在。版本文档中不可提前写“测试已通过”“已上线”。需要补充源码中的发布说明时先修改并提交，再重新测试；不把带自身 commit SHA 的通行证写回同一个被测提交。

## 3. 文档组织和单一事实来源

- 全局设计：[总设计计划](design-plan.md)、[产品约定](product/README.md)、[架构](architecture/README.md)。
- 执行规范：[AGENTS.md](../AGENTS.md)、[开发流程](standards/development.md)、[测试策略](testing/strategy.md)、[原生 E2E SOP](../sop/SOP-014-e2e.md)、[发布门禁](standards/release.md)。
- 每轮档案：`releases/<release_id>/` 下的需求、拆解、开发计划（含技术设计引用）、测试计划、发布预案、迭代记录及 `00-manifest.json`。
- 跨版本索引：[功能矩阵](../tests/feature_matrix.json)、[数据集清单](../tests/datasets.json)、[Changelog](../CHANGELOG.md)。
- 实际状态：[当前状态](status.md) 和机器执行证据；规划项不能代替实现状态。

全局文档保留长期约定，版本档案记录本轮变化并链接全局文档，避免每轮复制全套规格。代码与文档不一致时先确定预期行为并修正，不能让测试以错误实现为答案。

## 4. 初始框架版本的历史交付边界

初始框架版本 `v0.0.1-20260929T060944Z` 建立全流程框架、首版设计和文档基线；已有脚本只验证规范/合成数据并明确阻断产品发布。当前没有账号系统、日志采集 App 或真实产品 E2E。

下一轮产品开发从 TM-001 开始，先建立该版本完整档案，再按 SOP-009 建立可运行工程骨架、按 SOP-010/011 取得登录及必要发布基础的真实业务失败证据，然后实现完整业务链路和自动 E2E。测试、数据程序和 SOP 从第一项功能开始一起交付。
