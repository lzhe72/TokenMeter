# 文档驱动的全流程框架

这是 TokenMeter 的工作顺序。最高规则是“规范驱动文档，文档驱动设计、开发、测试、发布和迭代；每一步必须有 SOP”。先确定流程和文档合同，再基于文档实现产品，之后重复同一流程迭代。每轮由唯一 `release_id` 贯穿。[文档标准](standards/documentation.md) 定义文档合同，[SOP 总索引](../sop/README.md) 定义大模型如何执行每一步。

```text
定义 SOP 总索引及独立文件
  → 编写 SOP、规范与模板
  → 版本立项与档案建立
  → 需求定义
  → 功能拆解
  → 技术设计与开发计划
  → 测试计划
  → 发布预案
  → 文档基线完整性检查
  → 按文档开发 / 编写测试 / 生成数据
  → 自动执行 E2E / 失败修复与回归
  → 自动判定门禁 / 生成发布记录与通行证
  → Git tag / Release / 部署分发
  → 收集问题并建立下一轮版本需求
```

## 1. 每一阶段的输入、输出和完成条件

| 阶段 | 输入 | 必须产生的文档/产物 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| SOP 清单与定义 | 所有工程阶段和执行动作 | [SOP 清单](../sop/README.md)、每份 SOP 的输入/步骤/输出/判据/恢复 | 无未覆盖步骤，每份 SOP 可指导大模型执行 |
| 版本立项 | 已确认目标及上版结果 | release_id、manifest、当前索引、迭代记录 | 编号合法且唯一，范围和输入明确 |
| 需求定义 | 用户目标、使用场景、上版问题 | requirements.md：用户、范围、权限、可验收行为、非目标 | 每条需求有稳定 ID 和可观察的验收条件，无影响架构的未决问题 |
| 功能拆解 | 已确定需求 | breakdown.md：需求→功能→子任务、依赖、版本目标 | 所有需求被功能覆盖，边界和依赖明确 |
| 技术设计 | 功能拆解与当前实现 | 模块/接口/数据/兼容和恢复设计 | 设计可实现且可验证；与需求、权限和数据约束一致 |
| 开发计划 | 功能/任务与架构约束 | development-plan.md：实现顺序、模块/接口/数据变化、兼容/迁移、风险、交接 | 每个任务可执行，输入输出与完成标准明确 |
| 测试计划 | 需求、功能及开发计划 | test-plan.md：用例、账号/数据、生成与重置程序设计、独立预期、SOP、自动 E2E、环境矩阵 | 每条验收条件映射用例；每个场景有数据与自动执行方案 |
| 发布预案 | 本次版本范围、测试计划 | release-plan.md：计划内容、发布条件、安装/部署、升级/恢复、预计证据清单；Changelog 版本条目 | 上线条件可由门禁程序判断，不能出现“测试后补” |
| 文档基线 | 上述计划文档与 manifest | 同一 release ID 的完整版本档案 | 文档互相一致，需求/功能/任务/测试/发布要求可双向追踪 |
| 开发与测试 | 完整文档基线 | 功能代码、真实测试、数据/账号程序、可直接执行的 SOP | Codex 按计划实现，变更时同步文档，不自行偏离验收行为 |
| 自动验证 | 候选提交、构建物、测试环境 | 原生 E2E 报告、日志/附件、机器判定 | 目标与历史回归完整通过；失败修复后重新完整验证 |
| 发布与归档 | PASS 通行证与对应产物 | annotated tag、Git Release、发布资产、实际发布记录 | 提交、版本、证据、产物摘要一致；发布只使用被验证的产物 |
| 产品迭代 | 用户反馈、缺陷、运行数据 | 新 release ID 和新需求档案 | 不改写历史 tag/通行证，按同一流程启动下一轮 |

上述完成条件是文档和机器检查条件，不额外引入每一步都要用户手工批准的流程。需要产品决策时明确提问；常规实现和测试由 Codex 自主完成。

## 2. 文档先行不等于预填通过结果

开发前写发布**预案**，明确要发布什么、如何验证、如何上线、如何恢复。测试与发布实际发生后，由程序生成带时间、提交、产物摘要和结果的**执行记录**，附在 CI/Git Release 版本资产中。

发布预案可以提前存在；PASS 通行证不能提前存在。版本文档中不可提前写“测试已通过”“已上线”。需要补充源码中的发布说明时先修改并提交，再重新测试；不把带自身 commit SHA 的通行证写回同一个被测提交。

## 3. 文档组织和单一事实来源

- 全局设计：[总设计计划](design-plan.md)、[产品约定](product/README.md)、[架构](architecture/README.md)。
- 执行规范：[AGENTS.md](../AGENTS.md)、[开发流程](standards/development.md)、[测试策略](testing/strategy.md)、[原生 E2E SOP](../sop/SOP-014-e2e.md)、[发布门禁](standards/release.md)。
- 每轮档案：`releases/<release_id>/` 下的需求、拆解、开发计划（含技术设计引用）、测试计划、发布预案、迭代记录及 `manifest.json`。
- 跨版本索引：[功能矩阵](../tests/feature_matrix.json)、[数据集清单](../tests/datasets.json)、[Changelog](../CHANGELOG.md)。
- 实际状态：[当前状态](status.md) 和机器执行证据；规划项不能代替实现状态。

全局文档保留长期约定，版本档案记录本轮变化并链接全局文档，避免每轮复制全套规格。代码与文档不一致时先确定预期行为并修正，不能让测试以错误实现为答案。
