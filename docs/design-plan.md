# TokenMeter 产品功能完善方案

设计基线编号：`v0.0.1-20260929T060944Z`。先按 [全流程框架](lifecycle.md) 完成文档基线，再进入文档驱动的开发、测试和发布，之后按同一流程迭代。本文件汇总已确认决定，具体执行合同由下方文档和版本档案承接。当前是设计与工程基础阶段，未实现产品 App/服务端，产品 E2E 为 BLOCKED。

## 1. 第一项：建立 SOP 总索引和独立执行文件

[SOP 总索引](../sop/README.md) 是唯一执行入口，按工作名称、触发条件、前置条件、详细文件、必需输出、后续步骤、状态和修订版本查找流程。新增功能、修复问题、发布版本、文档维护的导航复用同一套文件。

根 `sop/` 下有 SOP-000 至 SOP-024 共 25 份独立文件，按工作步骤拆分：规范维护、版本立项、需求、功能拆解、技术设计、开发计划、测试计划、发布预案、基线检查、环境、数据、测试实现、开发、基础检查、原生 E2E、缺陷修复、迁移、安装包验证、门禁、Git 发布、部署、回退、归档、迭代、文档变更。

每份固定为：**目的与范围 → 触发条件 → 前置条件 → 输入 → 执行步骤及命令 → 输出 → 成功与失败判据 → 异常恢复 → 证据位置 → 下一步**。执行顺序依据依赖；迁移、回退按条件触发。尚无真实程序或环境的操作标明 BLOCKED。

[AGENTS.md](../AGENTS.md) 强制：做事第一步读总索引，再完整读对应独立 SOP；验证输入、按步骤执行、验证输出并保存证据。不得仅凭摘要或记忆跳过详细流程。缺规范或存在冲突先按 SOP-000 修订；明确的用户指令优先，并记录、同步受影响规范。

完成 SOP 体系后建立规范和模板，再完成需求、拆解、技术设计、开发计划、测试计划、发布预案和文档基线，随后进入开发与验证。

## 2. 已确认的产品目标

构建 macOS 桌面 App TokenMeter，统计个人与团队在大模型工具中的 Token 使用量和估算费用。首版重点是数据可核对、来源透明、团队权限正确、升级可靠，并且每项功能均可由 Codex 自动开发和验证。

| 议题 | 已确认决定 |
| --- | --- |
| 数据来源 | 只读本地 Codex、Claude Code 已有日志；用户不修改 API 地址，不引入代理或新遥测配置 |
| 模型范围 | 日志中可识别的 GPT、Sonnet、Opus、Qwen、GLM 等；保留实际标识，未识别数据明确提示 |
| 监控含义 | 覆盖这两个工具实际记录的调用；无法承诺任意 App/独立 API/全部历史自动可见 |
| 使用对象 | 团队集中管理，一套服务一个团队，成员看本人、管理员看团队 |
| 首次体验 | 首次启动说明、登录、工具/目录选择、系统授权、数据预览、确认同步 |
| 账号 | 无开放注册，管理员预置；首次改密、重置、停用、退出和设备解绑 |
| 统计 | 今天、昨天、近 7/15/30 天可配置、自定义日期、趋势/明细/模型/成员/项目统计 |
| 费用 | 按价格版本估算，包含缓存语义；未知价格不填零，分币种统计，订阅费用标注折算 |
| 数据库存储 | 客户端 SQLite 文件；服务端试运行 SQLite，正式生产 MySQL；具备备份、迁移、恢复 |
| 软件更新 | 更新服务器自动发现版本，App 展示版本说明，用户点击后安装与重启；签名校验和恢复测试 |
| 测试 | 每项功能有用例、测试用户/数据程序、SOP；每次迭代/修复/发布自动执行 E2E，未通过不能上线 |
| 开发方式 | Codex 按 AGENTS.md/docs 开发、编写测试、造数、执行、诊断、修复、判断发布门禁 |
| 版本追踪 | 版本号+UTC 时间的 release ID，连接需求→拆解→开发计划→测试计划→发布文档→Changelog→通行证→Git tag |

详细行为、统计口径、隐私与默认值见 [产品约定](product/README.md)。预算提醒、CSV 导出、菜单栏和诊断也纳入首版功能分解，共 TM-001 至 TM-012。

## 3. 架构与关键数据设计

采用 SwiftUI 原生客户端、FastAPI 单体服务端。日志适配器按经过验证的工具版本读取，归一化后写入本地 SQLite，并经离线队列同步至团队服务端。服务端负责认证、权限、幂等接收、汇总和管理。接口使用 `/v1`。

必须处理重复扫描、累计计数、会话分支、子代理、日志半行/移动/清理、网络故障、重复上传。未知值和历史缺失必须可见。费用与统计不上传对话/代码正文或完整本机路径。架构、接口、数据字段及生产迁移边界见 [架构设计](architecture/README.md)。

默认团队时区 Asia/Shanghai，存储 UTC；近 N 天包含今天。文件变更增量读取、30 秒补扫、60 秒同步；可手动刷新。首次导入默认 30 天，本地保存 90 天、服务器 365 天；未同步数据不得被常规清理删除。

## 4. Codex 开发与文档体系

- 最高约定是“规范驱动文档，文档驱动设计/开发/测试/发布/迭代；每一步有 SOP”。[文档标准](standards/documentation.md) 规定格式、状态、关联和更新规则，[SOP 索引](../sop/README.md) 覆盖制定规范、需求到发布和下一轮迭代。
- [AGENTS.md](../AGENTS.md) 是仓库开发入口，约束测试、数据、隐私、Git 和完成报告。
- [开发流程](standards/development.md) 固定“需求/用例→数据程序→实现→测试→修复→门禁”的自动闭环。
- 功能使用 [功能模板](templates/feature.md)，问题修复使用 [修复模板](templates/bugfix.md)，为后续会话保留可复现上下文。
- [当前状态](status.md) 只记实际完成、执行结果、阻塞与下一步。功能代码、接口、数据库、命令变化时，同次更新对应文档。
- 功能、用例与数据登记在 [机器功能矩阵](../tests/feature_matrix.json) 和 [数据集清单](../tests/datasets.json)。计划中的用例明确为空绑定，不能冒充已执行测试。

编制期间逐步执行 `check_docs.py --mode structure`；计划齐全后由 SOP-008 执行 `--mode baseline`。技术设计先于开发计划完成，可作为计划中的设计章节或独立附件。版本计划的程序绑定可以为 planned；已有路径必须有效，009–011 建立真实程序后改为 ready。文档基线只验收计划，不要求后序工程已实现。基线通过后先建立工程骨架，再编写数据与行为测试、实现业务；缺环境时继续可独立验证的子任务，真实运行保留 BLOCKED。

## 5. 自动 E2E 是迭代和发布前置条件

每项功能必须具备需求 ID、验收条件、正常/失败/边界用例、测试用户和数据生成/重置程序、独立预期值、可执行 SOP、真实 E2E 绑定和证据。数据和账号准备不能依赖人工操作，SOP 必须能被 Codex 直接执行。

[独立验收清单](../tests/acceptance.json)保存全部批准条件及所需数据能力，检查程序比较产品规格、验收登记和用例双向覆盖。目前规划 12 项功能、34 个场景；删掉用例而保留需求会失败。基础 USD 价格样例与待实现的历史价格、多币种、订阅数据分开登记，避免把部分数据当成完整前提。

真实链路：原生 App UI → 登录/授权 → 日志读取 → SQLite → 队列/网络 → 真实服务与数据库 → 成员/管理员界面/导出断言。不能用 API 自测或截图代替整个桌面产品 E2E。

每次迭代执行目标功能及所有已交付功能回归；发布再验证最终签名包的干净安装、升级、数据库迁移/恢复与所有声明支持的平台。数据、预期、服务、时钟、故障注入和重置由程序控制。

Codex 自动读取结果，失败后定位并修复，再执行完整回归。没有测试、零用例、跳过、失败、环境缺失、未经解释的不稳定结果或证据不一致，都不能放行。详细要求见 [测试策略](testing/strategy.md)、[E2E 执行 SOP](../sop/SOP-014-e2e.md)、[发布门禁](standards/release.md)。

当前TM-001已接入App、服务和真实原生runner，实际验收结果统一见[状态页](status.md)。缺原生运行环境或有效证据时为BLOCKED，最终发布另受签名/公证/全矩阵/受保护签发条件限制；文档或基础工具通过不能替代这些条件。

## 6. 全流程版本与发布通行证

`release_id = vMAJOR.MINOR.PATCH-YYYYMMDDTHHMMSSZ`，在迭代开始时固定。需求、拆解、开发计划、测试计划、发布说明存入同名版本档案；Changelog 二级标题、commit 信息、最终 Git tag/Release 使用同一编号。

每个编号能查到功能与测试程序、报告、提交和发布资产。发布通行证由自动门禁依据真实原生结果生成，绑定最终 commit、安装包/服务端摘要、数据与用例摘要、支持矩阵和 CI 身份；仅 PASS 可签发。失败或 BLOCKED 无通行证，不创建发布 tag。

常规 CI 运行 iteration；候选工作流从默认分支发起，按完整 SHA 在创建 Tag 前运行 release 门禁。正式发布任务随后消费该候选的有效通行证和原产物，创建同名 Tag/Release。当前候选入口已落地，可信证据签发与远端保护仍未接通，不具有发布资格。

命名、目录、查询、证据保存及避免提交 SHA 循环的规则见 [版本规范](standards/versioning.md)。本设计基线的 [版本档案](../releases/v0.0.1-20260929T060944Z/00-manifest.json) 已登记全部文档与验证入口。

## 7. 实施顺序与验收

实施顺序为：确认方案 → SOP 索引及 25 份细则 → 规范/模板/AGENTS.md → 完整计划文档与基线 → 环境/数据/测试/门禁 → 逐功能开发验证发布 → 反馈迭代。迁移已有草稿时保留其有效内容，并记录旧入口的替换关系。随后在 0.1.0 登录功能中接通真实 App/服务端/数据库和 UI E2E，从第一项产品功能开始自动验收。之后按功能逐版交付授权、两类日志采集、统计、费用、团队同步、导出、预算、更新、迁移与诊断；版本表见 [路线图](roadmap.md)。

正式发布前必须落实完整 Xcode、可交互的 Mac runner、支持平台矩阵、签名/公证、隔离数据库、受保护 CI 检查和发布凭据。缺少条件时 Codex 精确报告阻塞并继续独立工作，不要求人工填写通过结论。

版本依赖已细化：0.1.0 验收本人身份与账号管理，并交付最小签名更新器；统计权限和停用上传在 0.7.0 验收。0.2.0 验收目录授权，恢复后的日志去重在 0.3/0.4.0 验收。首版验证干净安装及候选→受控高版本测试包的真实更新，自 0.2.0 起每版验证上一公开稳定版升级；0.10.0 完善设置、说明和异常体验。开发阶段的隔离开发签名与发布阶段的最终签名包分别验证。

最终成功标准：同一数据经重扫、重启和断网恢复后总量仍正确；权限和隐私符合约定；每项功能及历史回归都有程序、SOP 和实际通过证据；一个 Git 发布编号可追溯完整需求、计划、测试和通行证。
