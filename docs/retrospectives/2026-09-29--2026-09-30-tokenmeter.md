## 三、复盘案例

### RET-001：仓库绑定成功，提交仍然推送失败

**问题与影响：** 初始目录克隆、remote 和本地 commit 都成功，用户却看不到远端内容；随后 `gh auth login` 被 `127.0.0.1:33210` 的残留代理拒绝连接，用户又将设备授权码误认为邮件或短信验证码。

**决策过程：** 分别检查 Git 历史、remote、认证工具和终端代理。确认问题发生在认证/网络层，没有丢失本地提交。安装并校验 GitHub CLI 后，说明设备码来自运行命令的终端；用户完成浏览器认证。

**解决方案：** 对报错的终端会话清除失效代理变量，执行 GitHub CLI 浏览器登录及 Git 凭据配置，再推送原提交；不重建仓库或复制提交来绕开认证问题。

**落地结果：** `2af0d8b` 已推送 master。对话中用户明确返回认证完成，后续远端历史也包含该提交。依据：“绑定 TokenMeter Git 仓库”全部 9 个 turn。

**经验借鉴：** 将“本地 commit”“远端 push”“CI 验证”“master 合并”分别报告；认证错误优先核对实际命令环境中的代理和凭据。需要用户完成个人认证时，给出具体操作位置与成功标志。

### RET-002：用户要求完善方案，执行却提前进入文件实施

**问题与影响：** 用户连续补充全流程、E2E、文档规范和 SOP 规则时，助手提前修改文件。用户明确指出应先整合聊天、更新《TokenMeter 产品功能完善方案》，确认后再实施。

**决策过程：** 助手承认提前实施，停止继续改动，保留未提交文件，回到完整方案。后续用户明确发出 `PLEASE IMPLEMENT THIS PLAN` 后才按最终方案整理落地。

**解决方案：** 在方案阶段明确当前输出和状态；确认最终方案时将变化合并到单一设计入口，实施阶段从该基线执行。已经存在的未提交工作先核对归属，不直接覆盖或假定它已获批准。

**落地结果：** 基础版本记录保存了从旧草稿到新索引的迁移与编号映射。对话定位：主线程用户消息 `01a0ebd7-c452-77b0-92da-6c8d2b19d2ec`；后续实施见 `b9acb29`。这次纠正不意味着以后每次常规执行都需要再次确认，用户后续已持续授权开发和合并。

**经验借鉴：** 先确认当前任务是方案修订还是已授权实施。不能用行动速度替代对用户当前阶段的理解；授权已明确后也不应反复停止索取同一许可。

### RET-003：SOP 清单不等于可执行的 SOP 索引体系

**问题与影响：** 早期方案列出一组流程名称，混有工程专项与协作主体。用户要求大模型先查唯一索引，再找每一步独立 SOP，按工作步骤拆分。

**决策过程：** 以用户澄清为准重新组织 25 个步骤；AGENTS 统一入口，索引负责导航，独立文件负责前提、命令、证据、成功标准和异常恢复。原有编号迁移单独留表，避免历史引用变成另一项工作。

**解决方案：** 根目录 [AGENTS.md](../../AGENTS.md) 强制先读 [sop/README.md](../../sop/README.md)，再全文读取 SOP-000–024 中的相关文件；索引列依赖和下一步，缺规范先维护规范。执行主体不作为分类目录。

**落地结果：** 25 份 SOP、目录检查及模板随基础 PR #1 合并；旧 `docs/sop/` 未保留为第二套当前入口。依据：基础版本执行记录及 `b9acb29`。

**经验借鉴：** 索引必须能回答“现在做什么、读哪个文件、缺什么、产出什么、下一步是什么”；只有标题清单无法驱动自动执行。

### RET-004：版本编号和文件顺序无法直接贯穿交付链

**问题与影响：** 用户要求 Git 编号包含版本和时间，并能反查需求、测试和通行证；版本目录按字母排序时先出现 breakdown，执行顺序不直观。

**决策过程：** 统一立项分配一次 `vMAJOR.MINOR.PATCH-YYYYMMDDTHHMMSSZ`，不为每个中间提交创建发布版本；将索引与步骤分开编号，保留文档逻辑 ID。

**解决方案：** `00-manifest.json` 连接 `01-requirements` 至 `06-iteration-record`；同步模板、链接、校验器和版本查询。分支、commit、Changelog 二级标题、最终 Tag/Release 均关联 release_id；通行证在候选后作为资产生成。

**落地结果：** `3470b49` 完成编号；工具回归增加未编号/错序拒绝。后续 TM-001 从 `151ed75` 的计划基线开始，使用同一发布编号追踪至 PR #2。依据：[版本规范](../standards/versioning.md)与两版 manifest。

**经验借鉴：** release_id 表示本轮交付，commit SHA 表示实际源码，run_id 表示一次执行，artifact hash 表示具体包。四者都要关联，不能用一个编号代替所有身份。

### RET-005：规范检查通过，流程仍存在循环和覆盖漏检

**问题与影响：** 用户要求整体审查后，发现工具 70 项通过仍存在 8 项流程/校验缺口和 1 项数据不足。尤其首次编写需求被迫先通过所有计划的基线，首次开发又被迫先提供依赖 App 的业务红测。

**决策过程：** 对 `3470b49` 做语义审查，并在临时副本删除场景、修改目录和绑定以实际复现漏检；用户明确要求修复后，先修规范再修检查程序。没有把文档能解析当作流程能执行。

**解决方案与逐项结果：**

| 原问题 | 修复与验证 |
| --- | --- |
| R01：草稿步骤依赖完整基线 | 增加 structure/baseline 两种检查；草稿可通过结构检查，严格基线仍拒绝草稿 |
| R02：工程骨架依赖业务红测 | SOP-009 先建真实骨架；planned/ready 分开，再进入业务红测与实现 |

### RET-015：本机更新需求被做成公网隧道，带来不必要的 DNS 阻塞

### RET-017：构建号断言超时，被误解为软件没有升级

**问题与影响：** run36663136535 第004例安装后等待 `app.build=101` 超时，最初无法判断失败在下载、安装、重启还是 UI；如果只看末尾断言，容易写成安装失败。

**问题与影响：** 为升级身份连续性探索 Apple Development/Developer ID 团队签名，用户明确仅内部使用，询问是否需要付费账号。把公开发行证书/公证当成全部开发的前提，会使已经可验证的工作停滞。

**决策过程：** 将 `distribution_profile=internal/public` 纳入版本合同；内部产品需求改变后不再强制本轮购买账号。空 `native-e2e-signing` environment 曾创建但无证书 secrets，后撤回；不是已经获得生产签名能力。

**解决方案：** 内部与公开分发分别列证据前提；内部仍需要固定候选、最终包安装升级、签名核验、全支持矩阵和受保护门禁，公开分支另要求 Developer ID 与公证。开发 CI 的临时身份只用于隔离验证。

**落地结果：** manifest 和 SOP-017/018 已区分 profile；最新源码迭代通过。内部最终包门禁本轮仍在实现，不能把“无需付费账号”写成“任何包都可直接发布”。依据：[发布规范](../standards/release.md)、TM-001 内部新基线记录。

**经验借鉴：** 先确认分发对象和运行方式，再选择签名与分发机制。简化不相关前提时保留实际需要的质量和证据标准。

### RET-019：用户需要方便登录，不是必须沿用 Keychain 机制

**问题与影响：** 用户先提出记住账号密码，再提出同设备自动登录。原来的跨签名 Keychain 会话恢复给内部升级带来弹窗，技术实现绑住了用户体验目标。

**决策过程：** 将需求明确为“在此设备上自动登录”，默认开启且可关；不保存明文密码，也不暗示硬件绑定。选择服务器随机、可撤销、固定30天到期 token，启动必须实际调用 `/v1/me`。

**解决方案：** 只持久保存 token，目录0700/文件0600、当前 UID、拒绝符号链接等异常路径、原子写、按 origin 隔离；关闭后本次登录仅内存。离线/到期/撤销不能恢复身份；退出先本地清理，未确认的服务撤销显示状态并仅在进程内重试。旧 Keychain 不迁移。

**落地结果：** `528859c` 实现；服务端45项、凭据组件13项与最终六例真实回归共同覆盖。文件范围内的“同设备”不是防复制的硬件证明，同 UID 进程仍可能读取文件；该限制写入设计。依据：[Auth.swift 中的凭据实现](../../apps/macos/TokenMeter/Auth.swift)、TM-001 需求/设计、E2E001/003/004/006。

**经验借鉴：** 从用户目标选择实现，不要求用户保留其未要求的技术机制。方便登录必须同时定义撤销、过期、离线和切换服务的行为。

### RET-020：六例断言都通过，父门禁却发现 xcresult 已变化

**问题与影响：** run36670563197 Intel 子报告六例 PASS，父校验为 `Native bundle was changed after execution`。初始摘要 `4048d992…` 与最终工件 `5040453d…` 不同；若只看子状态就会错误合并。

**决策过程：** 从原始 ZIP 只读逐项重算34个文件，确认确有字节变化；变化发生在过早摘要与解析/导出结束之间。现有证据不能严格区分哪个工具写入或 Xcode 延迟落盘，因此不把猜测写成确定根因。

**解决方案：** 子级在所有 `xcresulttool` 解析和附件导出结束后计算整个 bundle 摘要；父级在自身解析前后各重算并比较。SQLite 文件仍参与摘要。增加导出阶段写文件、父解析阶段写文件、失败路径保留摘要等负测。

**落地结果：** 父解析变化负测先真实失败，修后整合治理198项通过；最新两平台父门禁通过。旧 Intel 运行仍为 FAIL。证据：`.local/ci/loopback-parent-verifier-red.log`、`loopback-integrated-governance.log`、run36670563197/36674477502。

**经验借鉴：** 原始证据的生命周期也需要设计；工具读操作可能伴随写入。修复摘要时机，不排除发生变化的文件或关闭完整性检查来获得 PASS。

### RET-021：同机更新源落地，安全断言和默认配置也要真测

**问题与影响：** 用户提出两台 CI Mac 各自运行 App 和本机更新服务是正确的部署方式，但只把 URL 改成127.0.0.1还不足以证明默认配置和真实更新链能工作。

**决策过程：** 固定 API49176、更新源49177；默认地址由 App 自己使用，候选和高版本包不注入替代 feed；配置管理页可保存和恢复默认。保留 EdDSA、解压前验签及地址边界。

**解决方案：** 更新源只绑定127.0.0.1，端口占用即失败，不接管他人服务；随机 nonce 核验本次实例。第004例依次验证非回环 HTTP enclosure 拒绝、跳转到非回环 HTTP 的 ATS 拒绝、坏 EdDSA 包拒绝、有效包真实安装并自主重启；第006例覆盖设置保存与恢复。错误分类不允许用 DNS 失败代替安全拒绝。

**落地结果：** `3ad0d7e` 在两架构执行六例完整通过；真实构建号100→101与 `/v1/me` 恢复有原生证据。后台 fixture、真实下载签名和配置页一起测试，不依赖公网隧道。依据：run36674477502、[update_source.py](../../tests/e2e/update_source.py)、[原生用例](../../apps/macos/TokenMeterUITests/TM001AccountUITests.swift)。

**经验借鉴：** 测试拓扑尽量对应实际使用；让测试使用内置默认配置才能发现配置错误。回环 HTTP 例外需精确限定，不能扩展成允许所有明文 HTTP。

### RET-022：功能测试用例有机器清单，却缺少容易找到的人类阅读入口

**问题与影响：** 用户在 docs 中找不到每个功能点的 test case。此前细节分布在 `tests/acceptance.json`、`tests/feature_matrix.json`、版本04测试计划和 Swift 测试代码中，文档导航不能直接按功能查看操作步骤和预期。

**决策过程：** 将“已有机器绑定”与“用户可读的详细用例文档”分开核对；不能回答“JSON里有，所以文档已齐全”，也不能为了补文档声称未来11项功能已测试。

**解决方案：** 本轮补 [功能用例索引](../testing/cases/README.md) 和按 TM 编号的独立用例文档，保持 AC→E2E→数据→SOP→程序绑定，并区分 TM-001 已执行结果与其他规划用例。文档与机器定义同步检查，避免出现第二套互相冲突的验收条件。

**落地结果：** 本轮正在补齐入口和逐功能文档；其实际检查结果由本次执行记录登记。此前 run36674477502 只证明当前六例，不覆盖尚未实现的 TM-002–012。本案例不把新文档生成当成新产品测试。

**经验借鉴：** 规范可被机器执行，也应能被用户检索。每个功能页面至少给前提、账号/数据、步骤、独立预期、自动化入口和最近证据；缺一项时明确其状态。

### RET-023：合并成功的聊天结论已经更新，仓库状态文档仍停在上一候选

**问题与影响：** 本轮复盘开始时，实际 PR #2 已合并、CI36674477502 已 PASS，但 `docs/status.md` 仍写“新候选未执行、PR保持草稿、尚未合并”。新会话可能重复旧诊断或向用户报告错误状态。

**决策过程：** 通过远端 PR/CI API、Git tree 和本机 handoff 交叉核验，区分候选提交前写下的状态与之后发生的事实。不能为更新文字改写旧失败证据。

**解决方案：** 本轮在06记录追加实际合并和原生结果，状态页指向最新固定运行；保留旧候选问题在历史记录中。源码 PASS 与未完成包级门禁同时列出，避免把一个结果覆盖另一个。

**落地结果：** 当前执行负责人已修正 status 与06，记录分支头、测试合成提交、合并 SHA 和一致源码树。旧失败、旧诊断仍可查。依据：06“同机更新两平台通过与源码合并”。

**经验借鉴：** 工作完成包括更新交接入口。为避免“改一行状态就需再跑旧候选”的循环，运行证据作为候选后的不可覆盖资产保存；新文档明确引用被测 SHA，而不声称新文档提交已自动继承产品 PASS。

### RET-024：先承诺 macOS 14+，实际测试资源只覆盖 macOS 15

**问题与影响：** 初始方案把 macOS14+ 和两架构列为目标；当前可用 GitHub runner 与用户本机证据集中在 macOS15，不能据此证明14可安装、可升级或功能一致。

**决策过程：** 本轮发布准备核对平台资源后，用户明确以目前测试条件先走通链路，首个内部版支持 macOS15 Intel/Apple Silicon，暂不承诺14。此决定是公开范围调整，不是偷偷跳过已承诺场景。

**解决方案：** 同步产品、需求、技术设计、测试计划和发布门禁的支持矩阵；内部最终包仍需在声明的两平台完成验收，macOS14作为后续独立扩展目标建立环境和证据。

**落地结果：** 支持范围决定已进入本轮计划。run36674477502 的实际原生环境为 macOS15.7.9 两架构；新的最终包级矩阵尚待执行，不能把已修改的范围当作发行 PASS。依据：[本轮发布预案](../../releases/v0.1.0-20260929T074814Z/05-release-plan.md)、06 的支持矩阵决定。

**经验借鉴：** 先验证测试资源与最终包，再承诺最低平台；支持矩阵变化要由明确需求决定并同步全链路，不能只改 CI 标签或删除失败平台。

## 五、本轮之后如何使用这些案例

1. 新需求先从 [SOP 总索引](../../sop/README.md) 选步骤，核对本案例中相关用户约束；下一版本重新建档，不沿用上一候选的 PASS。
2. 遇到失败先按 RET-007/008/014 判断阶段，再对照证据。连续环境阻塞时按 RET-015 回看部署目标，不只追加重试。
3. 产品通过后按 RET-011/018/020 核验最终包和证据，完成 IMP-001 才可发行。
4. 任务交接按 RET-023 更新入口；对新事实追加记录，保留当时的失败和被推翻假设。
