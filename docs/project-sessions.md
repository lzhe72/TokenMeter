## 三、从需求到文档的交接

1. 需求会话负责产出可核对的事实：需求或用户决定、功能/TASK/TC ID、代码与数据变动、候选 SHA/tree、实际命令和退出码、原始报告路径、未完成与阻断。测试程序生成的不可覆盖原件可由执行会话保存；不得把原件摘要手写成测试通过。
2. 非 SOP 文档的变更请求交给“文档”会话，附目标文件、变更理由、上述事实和期望生效版本。本会话按 [SOP-024](../sop/SOP-024-document-change.md) 与[文档规范](standards/documentation.md)更新源文档、目录、导航、版本记录、Changelog 和 Excel；在独立工作树核对差异与检查结果，提供提交 SHA/tree 给开发总控。根项目总表的需求/任务/用例输入先于候选测试提交；一次测试的独立结果 Excel 随原始 run 生成且不覆盖；开发期真实测试批次在原始结果和独立结果表可读回后登记其实际状态，正式发行的通行证与归档另在用户启动该阶段后登记，详见[总表规范](standards/project-workbook.md)。
3. 需要修改 SOP 时，向“SOP”会话提交缺口、冲突、影响及依据；依赖该规则的下一步等实际修订与适用检查完成。SOP 会话若发现非 SOP 附件需变更，也交给“文档”会话。两种变更在总控整合时核对语义和引用一致。
4. 各需求会话使用独立worktree和同名功能分支；范围可核对的干净WIP/候选提交可按 [SOP-019](../sop/SOP-019-git-release.md)普通快进保存远端并读回SHA/tree，实际失败或未测状态原样登记。开发总控按版本顺序本地整合、逐版记录功能固定TC的真实回归状态，可选单一integration镜像；全部目标源码完成后按远端保护登记`master`并读回。用户另行启动正式对外发行时，对最终候选执行跨需求完整E2E与发行门禁，PASS并归档后登记正式Tag。功能分支、镜像和远端`master`源码登记都不能产生产品PASS。

**并发写入约定：** 从用户本次指令起，其他会话不再直接改写非 SOP 文档；指令生效前已存在的已提交或未提交文档改动作为待核对输入交给本会话处理，保留原始证据和草稿状态，不直接视为最终基线。执行会话只清理由自己创建且取得所有权的资源。文档更新不能改变冻结测试的输入、预期或包内容后继续借用旧候选的验收结果；具体按 SOP-024 与 SOP-019 判定。
