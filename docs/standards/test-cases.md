# 开发任务与测试用例规范

## 1. 强制顺序

**需求及验收条件 → 功能点 → 具体开发任务 → 逐项测试用例与数据设计 → 文档基线 → 测试程序与功能实现 → 按既定用例执行 → 逐项记录 → 门禁。**

需求阶段包含 SOP-002–008 的设计工作。测试用例在这个阶段写清；SOP-011 将已设计的用例编写成程序，SOP-012 实现对应功能。不能等功能做好后，再按现有代码挑几个能通过的操作作为验收。

当前已存在的实现保留，用于检查与需求的差距。补充的用例属于本次基线修订，不能声称它们先于历史代码编写，也不能将旧的汇总 PASS 回填为新增用例的结果。需求缺少关键预期时登记 `baseline_pending`，返回 SOP-002/004 明确，再继续依赖任务。

## 2. 开发任务怎么拆

每项任务有稳定 `TASK-` 编号、所属需求/功能/验收条件、具体输入、实现产出、依赖和完成条件。任务描述必须可直接交给实现者，例如“校验登录输入并显示错误”“校验凭据并创建会话”“恢复会话前调用身份接口”。“开发客户端”“实现后台”“测试一下”只能作为工作分组，不能代替具体任务。

每项任务至少对应一个稳定 `TC-` 用例。一个任务通常有多个用例；一个跨模块用例可以关联多个任务。纯文档、数据或执行器任务也需可验证的检查用例，但不能冒充产品 E2E。已有 `E2E-` 编号保留为执行场景组，组内用例分别判定。

## 3. 每条用例必须写什么

使用[用例模板](../templates/test-case.md)，包含：

| 字段 | 要求 |
| --- | --- |
| 身份 | TC ID、标题、release_id、REQ、TM、AC、TASK、所属 E2E 场景组、测试层级 |
| 预期依据 | 指向具体需求/设计段落；未规定的文案、状态码、边界不能从当前实现倒推 |
| 前置条件 | App/服务状态、身份权限、会话/数据库初态、网络、配置；独立或有序依赖明确 |
| 输入和数据 | 实际账号、具体密码/构造规则、初始行、种子、参考时间；生成程序、SQL、重置和 SOP |
| 操作和预期 | 每一步分别写输入、动作、UI 预期、API/数据库/文件或进程预期、取证方式 |
| 完成断言 | 可以判真假的结果；失败输入也要检查没有产生会话/越权/数据副作用 |
| 执行与清理 | 真实自动化入口或 null；缺失项、准备任务、清理归属、证据路径 |
| 状态 | 设计状态、程序绑定状态、执行状态分别登记；未执行不能写 PASS |

不适用的观察面写“不适用”并说明理由。不要只写“登录成功”“结果正确”“按预期”。服务端密码应按已确定的认证合同校验哈希；测试 DB 提供合成用户和只读核对依据，App 不直接连接数据库比较明文密码。

参数化测试的每一行输入必须有独立 TC ID 或稳定的变体 ID，记录每一行的操作和结果，不能用“覆盖所有非法输入”代替枚举。共用准备步骤可以引用同一配方，不能省略本例的实际输入和预期。

macOS 系统凭据属于独立测试资源。调用 `safeStorage` 的 TM002/003/004 用例在运行前写明最终包、签名、实际测试 Keychain service/account（或提供者等效身份）的原生核对方法、与正式 App 的分离证据、预存 item 的阻断条件和本次创建 item 的精确清理断言。`--user-data-dir` 或每例新 profile 只证明文件目录隔离，不证明 Keychain 隔离。源码可用于设计预期，不能代替同一最终包的实测；缺机器可执行的身份/归属判据为BLOCKED。

## 4. 场景覆盖检查

按任务适用性列出正常、错误组合、空值、格式/长度边界、权限、持久化/重启、网络/服务故障、重复/并发和安全拒绝路径。对不适用项说明原因，不机械生成无关组合。

例如登录的“正确用户名+正确密码”“未知用户名+错误密码”“正确用户名+错误密码”“未知用户名+另一个账号的正确密码”应分别列出。错误提示相同也要独立执行与记录，因为失败原因和潜在缺陷不同。

每个 AC 至少被具体任务和 TC 承接；每个任务至少有 TC；每个 TC 都能回查任务和预期来源。保留未来功能的概要场景，但在进入该功能开发前必须完成同样的细化。

## 5. 每次执行怎么记录

运行记录由程序产生并保存到本机独立目录。规范定义以下记录合同；执行器没有实现这些字段时，状态为绑定待补齐，不能用手写报告替代。

| 层级 | 必须记录 |
| --- | --- |
| 一次运行 | run_id、执行原因、范围（定位/完整回归/最终包）、release_id、候选 SHA/tree/dirty、App/安装包与用例基线摘要、平台、数据/SQL/配置摘要、开始/结束时间 |
| 每条用例 | TC/变体 ID、TASK/AC、实际输入引用、前置检查结果、程序入口、开始/结束时间、PASS/FAIL/BLOCKED、未执行原因 |
| 每一步 | 步骤编号、实际动作、预期值、实测值、比较结果、时间、原始日志/trace/截图/只读数据库证据引用及摘要 |
| 失败与清理 | 首次失败步骤、后续未执行步骤、缺陷编号、根因/修复关联、资源归属及清理结果；后续清理单独追加，不覆盖原失败 |

记录只用合成测试账号；真实密码、token、密钥不写入报告。随机值通过稳定的数据引用和脱敏摘要追踪。详细格式模板见[执行记录模板](../templates/test-execution.md)。

每次实际运行必须按[总表规范](project-workbook.md)输出独立测试结果Excel，保留原始结果及源摘要。根项目总表只保留用例汇总、批次结果摘要和独立文件入口，不堆叠逐步实测。失败、阻塞也输出对应结果；历史聚合证据不能冒充新TC结果。

## 6. 何时运行与放行

开发中的定向测试用于验证一个明确变更或定位已观察失败；先记录执行原因、目标 TC 和预期验证点，再运行。相同代码、数据、配置和条件下，不无理由重复全量测试。修复、改动或环境恢复后按影响执行定向检查，形成候选后再做全部目标及已交付功能完整回归；定向通过不能替代正式回归。

设计基线完成、自动化绑定就绪、执行成功是三个不同出口。基线时允许未来程序为 null，但任务、用例、输入和预期必须明确。准备进入产品验收时，所有必测 TC 的数据、程序和逐步记录必须就绪。门禁按精确 TC 集合验证，缺例、漏变体、缺步骤证据、失败、跳过均不能放行；六个大场景组通过不自动证明其所有细化用例通过。

规范自身不等于程序已实现。执行器/门禁升级需作为具体开发任务，先设计治理检查用例再开发。未接通逐 TC 校验期间保留发布阻断；历史报告继续按当时合同保存，不修改为新的证据。

## 7. 固定程序与单例复现

测试必须是仓库中固化、可按TC编号重复执行的代码。输入、动作、预期和断言在运行前确定；AI只能调用这些代码并分析原始结果，不能以临场操作、看图判断或手填结果代替测试。缺自动化绑定或缺可执行判据为BLOCKED。

- 产品入口：`scripts/run_test_case.py --case-id TC-ID --package-manifest <实际包清单>`；`--all`完整回归。开发诊断包必须显式带`--development`。 当前源码的新运行不带`--source-report`；重放历史报告时加该参数，程序核对测试代码与包摘要，源码不同则拒绝执行，先恢复对应版本或明确建立新批次。
- 父TC自动展开全部已声明变体；也可指定一个`TC-ID#变体`定位。每次自动生成新run_id和新输出目录，原报告不覆盖。
- 固定操作/断言位于`apps/desktop/e2e/granular-*.spec.ts`，数据程序位于`scripts/granular_*.py`；成功认证必须使用真实服务。
- Excel列出稳定TC、源码绑定、独立命令、用例及数据版本、机器断言和证据。截图只作为定位证据，不由AI看图决定PASS。
- 执行器、网络代理和固定时钟的组件自测单独标识，不能冒充App E2E。测试时钟只使用真实API已有的Python依赖注入，不改变生产时间或绕过认证。
- 证据复核同样使用固定代码。独立审计核验原报告和源码摘要，只能保留结论或将证据不足的PASS降为BLOCKED/FAIL，不修改原件。AI发现断言缺口后先固化审计规则，不能直接在Excel中手填通过。
