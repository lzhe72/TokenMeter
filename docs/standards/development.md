# Codex 自动开发与修复流程

## 每项功能的一次完整迭代

1. 先读取 SOP 总索引和对应独立文件，核对 AGENTS.md、当前状态及相关功能规格；按全流程框架建立 `releases/<release_id>/` 的需求、功能拆解、开发计划、测试计划和发布预案，再开始实现。
2. 使用功能模板写清用户路径、正常/失败/边界行为，在功能矩阵登记测试和数据依赖。
3. 通过 SOP-008 的完整基线后，先按 SOP-009 建立真实 App、服务、数据库初始化、原生测试 target/runner 的工程骨架，验证构建、启动与连通性；骨架不要求预先存在业务红测或产品 PASS。随后编写可重复生成/重置的账号、日志、时钟及故障程序，记录命令和独立预期。
4. 编写真实 UI E2E 与必要单元/集成测试，在可运行骨架上取得尚未实现目标行为的真实失败证据。骨架探针不能替代业务场景，环境/编译失败不能作为有效红测。测试入口必须经过真实认证。
5. 实现最小完整功能；运行局部测试，再运行本次目标及全部此前已交付功能的产品 E2E。
6. Codex 读取结构化报告和失败附件，判断功能问题、测试问题或环境阻塞；修复根因后在同一新提交候选上完整重跑。
7. 同步文档、矩阵、Changelog，提交候选代码。在干净提交上重跑最终门禁；提交后不能沿用提交前或另一安装包的通过结果。
8. 自动门禁为 PASS 后才具备发布资格；发布还需对应实际授权和部署凭据。完成报告附命令、退出码、证据路径、提交和阻塞项。

修复 Bug 遵循同样流程，并先添加能稳定复现原问题的回归用例。禁止只改预期值、删除失败用例、跳过平台或通过重试掩盖不稳定。

编制文档时，SOP-024 用 `python3 scripts/check_docs.py --mode structure` 检查草稿后返回原步骤；001–007 齐全才由 SOP-008 执行严格 baseline 与质量检查。技术设计先按 SOP-004 完成，可置于开发计划的独立章节或登记为单独附件，再按 SOP-005 编写实施计划。

## 编写给下一次 Codex 的上下文

- `docs/status.md` 保存实际实现状态、当前任务、已执行检查和阻塞，不写“应该已经通过”。
- 小型任务使用功能文档的执行记录；较长任务另建 `docs/work/<需求ID>.md`，记录决定、剩余步骤和恢复命令。
- 接口/数据库/命令改变时直接更新对应规范，避免只把决定留在聊天记录。
- 新增模块时可放置局部 AGENTS.md，记录该模块命令和约束；不要复制根文档全文。
- 多 agent 并行前划定文件所有权，整合后由主 agent 执行全量门禁；子 agent 的“完成”不是集成测试证据。

## 遇到阻塞

缺少 Xcode、GUI 会话或原生执行器时，依赖这些条件的构建、运行与验收返回 BLOCKED，列出精确恢复条件。Codex 可按开发计划继续完成有独立验证条件的源码、fixture、文档和测试编写；已有真实测试/数据绑定仍须保留，不能把源码完成当作行为红测或验收通过。工具链恢复后补齐失败基线和完整回归。开发 E2E 可使用隔离开发签名包；生产签名、公证和发布凭据只阻断 SOP-017/018 的最终包及发布验证，发布必须单独验证最终签名产物。
