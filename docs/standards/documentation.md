# 文档规范

> 2026-09-30当前执行基线：[Electron本机设计](../architecture/01-electron-local.md)。Electron/React/TypeScript、Vite/electron-vite、Playwright Electron、electron-builder；本机开发/全量测试/打包，当前仅macOS15 Intel实测范围。Git保存源码/文档/版本；DMG、更新包、报告和通行证只存本地，Actions仅明确多环境要求时启用。正文中旧Swift/XCUITest/双CI/受保护CI或GitHub Release过程仅是历史设计，不是当前执行入口。每项功能真实E2E与发布门禁不变。

## 最高执行规则：每一步先有 SOP

执行任何工作第一步读取 [SOP 总索引](../../sop/README.md)，再完整读取对应独立 SOP，核对前置条件与输入。缺少、冲突或不可执行时先按 [SOP-000](../../sop/SOP-000-maintenance.md) 维护规则。每一步验证输出并保留证据；不通过不得推进依赖步骤。明确的用户指令优先，差异记录并同步规范。

SOP 的新增、修改和删除集中在「SOP」管理会话（thread ID `01a0f5a5-63f7-76b0-aa53-ac6befec91ef`）执行。其他会话发现缺口时通知该会话并交付依据、受影响流程及当前阻断；管理会话按 SOP-000 修订和回告。这个分工不改变各工作步骤的先后依赖或验证门禁。

每份 SOP 必须包含：修订、状态、适用范围及十个固定章节：**目的与范围、触发条件、前置条件、输入、执行步骤、输出、成功与失败判据、异常恢复、证据位置、下一步**。纯文档步骤同样需要输入、确定的编辑动作和结构/引用验证方法；涉及测试与发布的步骤必须使用真实执行结果，不能靠人工勾选通过。

全部 25 份 SOP 按工作步骤拆分，索引负责导航，独立文件负责执行。测试数据细节见[测试执行参考](../testing/execution.md)。机器文档目录的 `sop` 字段必须指向根 `sop/` 下对应的独立文件，不能只填总索引。

## 1. 规范层级与单一事实来源

TokenMeter 按以下顺序推进工作，具体阶段见[全流程框架](../lifecycle.md)：

**规范 → 全局设计 → 每轮版本文档 → 开发与自动验证 → 不可覆盖的执行证据 → 下一轮需求。**

| 层级 | 记录什么 | 维护规则 |
| --- | --- | --- |
| 规范 | 工作顺序、文档合同、测试门禁、版本和发布规则 | 本文件、AGENTS.md、开发/测试/发布规范相互引用；不得各自定义冲突规则 |
| 全局设计 | 产品长期行为、架构边界、接口与统计口径 | 总设计计划汇总已确认决定；细节只在对应专题文档维护 |
| 版本文档 | 本轮需求、拆解、设计变化、开发/测试计划、发布预案 | 统一 release_id，说明相对基线的变化，链接长期约定 |
| 执行证据 | 实际提交、构建物、测试运行、门禁、通行证和发布结果 | 由程序生成；保留失败历史，不能把计划或手写结论当作执行结果 |
| 迭代复盘 | 实际结果、问题、根因、改进和下版需求 | 引用证据并分配后续需求，不能反向改写已发布结论 |

全局设计决定预期行为，版本文档决定本轮交付范围，机器证据决定实际是否通过。产品验收定义同时登记在独立 `tests/acceptance.json`，它与规格定义表及用例矩阵双向核对；不能用当前已有用例反向生成完整需求清单。文档与代码冲突时，Codex 先查明预期并修正对应文档或实现；不得用当前错误实现反推测试答案。

## 2. 最小文档元数据

每份 Markdown 源文档的元数据统一登记在[机器文档目录](../catalog.json)，可从导航按文档 ID 查询，正文无需重复所有字段。目录必须能解析到实际文件、输入、适用版本及 SOP。

| 字段 | 要求 |
| --- | --- |
| `doc_id` | 稳定且唯一，使用 `DOC-` 加字母、数字、短横线或下划线；改标题或路径不改变其逻辑身份 |
| `type` | 机器类型：`standard`、`design`、`plan`、`sop`、`template`、`record`、`index`、`instructions` 或 `changelog`；具体用途在正文说明 |
| `status` | `draft`、`baselined`、`superseded`，含义见下一节 |
| `applicable_release` | 具体 release_id；长期规范/设计使用 `all`，版本档案记录所引用的候选提交或基线 |
| `base_release` | 比较基线的 release_id；首次没有基线时明确为 `null` |
| `inputs` | 输入文档/需求/缺陷的 ID 和可定位引用，不能只写“见聊天记录” |
| `updated_at` | 本次有意义内容变更的日期，格式 `YYYY-MM-DD`；不是实际测试或上线时间 |
| `path` | 仓库内实际 Markdown 文件路径 |
| `sop` | 编写、维护和执行该文档时适用的 SOP 路径及入口 |

版本文档正文顶部保留 `release_id`，且必须与机器目录和版本 `00-manifest.json` 一致。[版本规范](versioning.md)定义统一编号和查询方法。机器目录检查至少覆盖必需字段、ID 唯一、文件存在、输入/SOP 引用、版本一致性和阶段所需文档；检查通过不意味着产品测试通过。

文档编制期间执行 `python3 scripts/check_docs.py --mode structure`：检查目录、已登记骨架、引用、版本档案和 Changelog 等结构，允许尚未完成的文档保持 draft，返回原 SOP 继续写下一份计划。SOP-001–007 的内容全部就绪后，SOP-008 执行 `python3 scripts/check_docs.py --mode baseline` 及 `python3 scripts/quality_gate.py check`；无参数默认为严格 baseline。结构通过不代表基线形成，不能据此开始依赖未完成设计的实现。Codex 同时核对语义、决定与验收条件，机器检查不证明产品 E2E 通过。

## 3. 三类状态必须分开

| 对象 | 状态 | 含义 |
| --- | --- | --- |
| 文档 | `draft` | 正在形成内容，可记录具体待解决事项，不能作为完整开发基线 |
| 文档 | `baselined` | 必需章节完整，关键决定已确定，关联和版本一致，可用于执行本轮工作 |
| 文档 | `superseded` | 已由明确的新文档/版本替代，保留原记录并链接替代项 |
| 功能 | `planned` / `in_progress` / `implemented` | 功能矩阵中的计划与实现阶段，遵循测试策略中的数据/测试绑定要求 |
| 一次运行 | `PASS` / `FAIL` / `BLOCKED` | 自动执行和证据校验结果，不能通过改文档或功能状态产生 |

`baselined` 不等于功能完成；`implemented` 不等于具备发布资格。模板使用 `type=template`、`status=baselined` 表示模板内容可采用，不表示按模板开展的工作已经完成。当前状态文档随事实更新并维护 `updated_at`，其中的产品状态仍独立记录。

文档基线通过一致性检查形成，不增加逐项人工批准流程。Codex 自主推进已授权范围；遇到无法从资料确定、会改变产品行为的决定时再明确提问。

## 4. 各类文档的必需章节

使用[全流程文档模板](../templates/lifecycle-bundle.md)。章节可以合并，但不能遗漏所需信息；同一信息通过链接引用，不重复抄写。

| 文档 | 必需内容 |
| --- | --- |
| 需求 | 用户与问题；本轮范围/非目标；稳定功能或需求 ID；权限、正常/失败/边界行为；可观察的验收条件；输入来源和未决项 |
| 功能拆解 | 需求→功能→任务对应表；任务输入输出与完成标准；依赖和顺序；本轮目标及未来项区分 |
| 架构/设计 | 当前行为与目标变化；模块与数据流；接口/数据/状态变化；权限隐私；兼容、迁移和恢复；关键决定及理由 |
| 开发计划 | 任务顺序和文件/模块边界；测试与数据准备任务；实现步骤；交接入口；完成标准、风险及验证方式 |
| 测试计划 | 验收条件→场景→数据→真实测试的追踪；角色/账号；生成与重置程序；独立预期值；可自动执行 SOP；安装后产品 E2E、故障场景和实际平台范围；证据与失败处置 |
| 发布预案 | release_id、范围和 Changelog；候选/构建方式；机器门禁；安装部署、升级/恢复；所需权限/环境；预期证据名称与位置；当前真实状态 |
| 迭代复盘 | 计划与实际对比；执行记录/通行证引用；未完成与阻塞；缺陷根因；改进任务和下轮需求；适用基线变化 |

技术设计可放在 `03-development-plan.md` 的独立设计章节，也可使用单独设计附件并登记、从开发计划引用；两种方式均有效，并引用全局架构。无论载体如何，SOP-004 先完成设计内容，SOP-005 再据此完成实施计划。无接口或迁移变化时写明“无变化”及核对依据，不能使用空白隐藏未判断的影响。

版本 manifest 的 `program_bindings_status` 单独记录程序准备情况：`planned` 允许 `test_programs=[]` 和 `test_data_program=null`，同时保留完整需求→任务→测试计划追踪及真实 `test_sop`，在任务中安排补齐程序；任何已填写路径必须真实存在。`ready` 要求测试与数据程序非空且可定位。省略该字段按 `ready` 严格检查，以保持旧合同约束。SOP-008 检查计划基线，不能要求后续 SOP-009–011 才要建立的程序预先存在；实际程序补齐后更新为 ready。ready 仅表示绑定就绪，不代表业务测试通过，当前治理工具 ready 也不代表产品就绪。

发布预案属于源码基线，实际发布记录属于执行证据。预案只能写待执行条件；实际时间、提交、产物摘要、E2E 结论和 passport 必须来自程序。没有真实通过证据时保留未发布状态，不预填“已通过”“已上线”。

## 5. 阶段进入与退出

1. **建立计划**：先查 SOP 总索引并完整读取详细文件，分配 release_id，登记文档骨架、输入及 SOP。按 001–007 顺序编制，未完成文档保持 draft；每次文档修改经 SOP-024 运行 structure 检查后返回原步骤。规划数据/测试尚未实现时记录任务及空绑定，不声称可执行。
2. **形成文档基线**：001–007 完成，需求、拆解、设计、开发/测试计划及发布预案齐全一致；每条验收条件有场景和数据/自动执行方案，关键未决项已解决。按 SOP-008 完成 baseline 与质量检查；不要求在需求编制时提前完成后续所有计划。产品实现不得先于本轮基线。
3. **准备工程、数据与测试**：SOP-009 按设计建立 App、服务、数据库初始化、原生测试 target/runner 的真实骨架，不以业务红测或产品 PASS 为其前提。可运行后经 SOP-010/011 准备数据与真实业务失败基线，再实现业务行为。功能进入 `in_progress` 前，数据集、数据程序与真实测试绑定必须齐全；源码已存在不代表执行通过。缺工具链时可完成有独立验证条件的子任务，构建/运行与验收仍 BLOCKED。生产签名和分发凭据在 SOP-017/018 检查，不作为开发前提。
4. **实现并验证**：按文档开发；变更决定同时修改关联文档、功能/用例清单、测试和 Changelog。执行本次目标及所有此前已交付功能的完整 E2E；未来无关规划项不加入本次集合。
5. **锁定候选与发布**：先提交源文档与代码，再在干净候选上构建、验证和生成不可覆盖的运行记录。只有本机机器门禁校验真实证据通过，才签发 passport 并执行发布；缺条件保持 BLOCKED。
6. **归档与下一轮**：记录实际结果和复盘，将遗留问题变成下一轮需求。新的版本 ID、文档基线和测试证据重新建立，不能复用旧 PASS。

完成条件由文档/机器检查及实际执行证据判断，不要求用户为每一步勾选批准。缺真实产品 runner 时，可推进不依赖其运行结果的工程准备与独立任务，不能将其标为产品测试通过或越过发布门禁。

## 6. 变更、记录和历史保留

- 每个步骤在版本工作记录中简要记录所用 SOP、输入、关键决定及理由、产出、实际结果、证据位置、未决项和下一步；记录采用追加方式，错误记录以更正条目说明。
- 命令、退出码、逐场景结果和构建摘要保存为机器产物；版本工作记录链接这些产物，不复制全部终端输出。凭据、真实会话正文和其他敏感内容不进入文档。
- 未发布候选的设计变化同步更新输入/输出引用和维护时间；已建立的基线发生变化必须重新检查。产品、测试、数据或发布配置变化后重新执行相应完整门禁。
- 已发布版本文档以对应 Git tag 中的内容为准，证据以对应不可覆盖的本地版本档案为准。纠错或新需求进入新版本，不移动旧 tag、不替换旧报告、不悄悄改变旧验收条件。
- 长期规范被替代时，在机器目录记录替代关系；旧版本仍能定位当时使用的规范。状态页可以更新当前事实，但不能重写历史发布证据。

文档检查和执行器的实现状态必须准确记录。仅添加本规范不代表机器目录检查、产品 E2E 或发布自动化已经实现。

## 7. 具体任务和测试用例先于实现

需求阶段建立需求→功能点→具体TASK→逐条TC的设计链；格式和逐步记录合同见[任务与用例规范](test-cases.md)。每轮提供流程导航、测试结果文档及实际发布记录；发布预案提前编写，实际发布记录由真实执行证据支持。根目录 TEST_CASES.md 在产品分支整合时汇总所有登记用例，详细文档保存完整步骤，两者关联同一稳定 ID；文件和固定程序尚未进入最终树时，依赖其验收保持BLOCKED。汇总文档不得把未执行或旧候选结果写成通过。
