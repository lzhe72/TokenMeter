# 项目总表维护规范

## 目的与入口

用户通过仓库根目录的[TokenMeter项目总表.xlsx](../../TokenMeter项目总表.xlsx)查看需求、验收、功能点、开发任务、用例汇总、测试批次索引、版本、复盘和SOP。项目文档与原始机器证据继续用于开发和追踪；总表须包含可读摘要，不能只有链接。

用户于2026-09-30最终指定本地Excel并随Git版本提交，随后明确总表中的测试用例只做汇总，每次执行单独输出测试结果Excel。腾讯在线文档没有写入，后续不自动向该链接上传数据。

## 数据与状态

- 每行保留稳定 REQ / AC / TM / FP / TASK / TC / release_id / run_id 中适用的编号，跨Sheet按编号关联。
- 测试用例表一例一行，包含功能、任务、类型、输入、预期结果、DB操作摘要和状态。总表不放逐步操作、逐例实测、原始事件或完整SQL表；详细设计保留在用例文档和 `tests/test_cases.json`。
- 开发任务包括实际产出和依赖；未细化的未来功能标“待需求阶段拆解”，不编造已实施任务。
- 测试批次表一次运行一行，记录run_id、版本、候选、范围、总结果、数量、摘要及独立结果Excel入口。父用例和参数变体分别统计，不能相加；完整回归与定向验证分开，概览以最近完整回归报告结论为准。用例汇总列出最近结果批次，来自不同批次的状态不能合成为一次全量PASS。新设计的TC未执行时写“未执行”；历史聚合组的结果不能填入新TC。
- 发布预案和实际发布状态分开。未取得有效通行证时，版本仍“未发布”，不能从完成率推算发布资格。
- Excel不收录真实用户会话、密码散列、token、私钥、生产DB或原始用户日志。合成测试输入及只读SQL可列入；本地原始证据通过摘要和相对位置追踪。

## 更新顺序

1. 先查 SOP-024 和本规范，更新本轮需求、任务、用例与实际结果的原始依据。
2. 同步结构化项目登记和用例清单；每条保留来源。只录入真实观察，不按当前实现编造预期。
3. 生成根目录用例集合和项目工作簿，检查编号唯一、任务/用例关联、状态和来源一致。
4. 核对各Sheet行数、输入、预期、DB摘要、批次及版本；检查筛选、冻结、换行、宽度、字体与状态提示，回读导出的xlsx。
5. 将总表xlsx、登记数据、生成程序和相关文档纳入同一Git变更。后续版本沿用根文件名；历史内容通过对应提交/tag查询。详细测试结果Excel与原始证据保存在本机，总表保留批次索引及相对入口；换机器需另行复制本地结果目录。

不把“表格已生成”写成产品测试通过。源信息或用例有变化时总表也要更新；不能只改总表而让实际开发依据失去关联。程序和检查的真实入口在完成后登记，尚未建立的自动更新不得声称可执行。

## 当前生成入口

- `tests/test_cases.json`：完整逐条用例、步骤、数据/SQL、绑定和真实执行状态。
- `docs/project-register.json`：本轮需求/功能/任务/SOP/版本/复盘及已观察历史运行的结构化快照；按其中source同步更新，不由现有代码反推内容。
- `python3 scripts/export_test_cases.py`：生成根目录TEST_CASES.md；加`--check`只读核对集合是否一致。
- `scripts/export_project_workbook.mjs`：使用Codex捆绑的Node与artifact-tool生成根目录xlsx；先用依赖工具定位运行时，将本轮`.local/workbook/node_modules`链接至其node_modules，然后用该Node执行此脚本。不得安装或修改依赖目录。
- 工作簿检查与预览位于`.local/workbook/`；检查不运行App，不生成产品PASS。生成后需回读xlsx，并按Sheet核对内容和显示，不能只以导出成功作为完成。
- 生成后运行`python3 scripts/verify_project_workbook.py`，从实际xlsx回读数量、完整回归状态、逐用例状态与证据批次、各批次计数和结果表路径，并扫描错误单元格。失败不得登记总表更新完成。

结构化登记与xlsx均进入Git；`.local`中的预览、工具原始检查及真实测试资产不进入Git。

## 每次测试的独立结果Excel

1. 按SOP-014执行测试，先保留真实原始结果；PASS、FAIL、BLOCKED均须归档，不能只输出成功批次。
2. 使用 `scripts/export_test_result.mjs --report <本次result.json> --output .local/test-results/<run_id>` 导出 `TokenMeter测试结果-<run_id>.xlsx`。使用与总表相同的Codex捆绑Node和artifact-tool依赖。
3. 结果工作簿包含运行概况、逐例结果、逐步动作/预期/实测、失败与缺证据、清理、环境/包/候选以及源文件摘要。原始结果没有的字段标为缺失，不能从用例设计或旧运行补造实测。
4. 同一源文件摘要重复导出时仅验证已有文件；输入变化必须使用新的归档目录，禁止覆盖已有批次。后续清理保留独立记录，不改写首次失败。
5. 生成与回读失败时记录报表归档未完成，保留原始产品结论；Excel本身不产生发布资格。本次执行和门禁结束后，再同步 `docs/project-register.json` 的 `test_runs` 摘要和总表。候选测试期间只写被忽略的本地结果目录，不能改动受Git追踪的总表或登记文件，避免破坏被测提交的干净状态。后续文档提交仍引用原被测SHA，不把文档提交冒充已测试候选。

`scripts/local_e2e.py`在原始结果写完后自动调用`test_result_export.py`。桥接程序核对原始JSON未变、run_id、Excel摘要及生成校验，写独立`excel-export.json`；导出失败返回非零，不改写产品PASS/FAIL/BLOCKED。默认使用Codex捆绑Node，可用`TOKENMETER_WORKBOOK_NODE`指定绝对可执行路径；需先准备`.local/workbook/node_modules`链接。

导出失败后修复环境，可直接用上面的Node命令指定全新归档目录补导原始结果；不需要重跑App。原失败收据和结果目录保留。接入情况及实际验证见当前状态文档；补导历史运行不构成一次新的产品测试。

## 可复现测试与证据

测试必须是仓库中固化、可按TC编号重复执行的代码。输入、动作、预期和断言在运行前确定；AI只能调用这些代码并分析原始结果，不能以临场操作、看图判断或手填结果代替测试。缺自动化绑定或缺可执行判据为BLOCKED。 独立结果Excel逐TC列出固定源码路径和单例运行命令；证据索引给出原件相对链接、SHA-256、实际断言及截图。源码、固定数据和报告的身份不一致不能标为通过。
