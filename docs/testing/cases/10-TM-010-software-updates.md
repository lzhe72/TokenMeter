# 10 · TM-010 软件更新：详细测试用例

需求：`REQ-TM010`。规划版本：`0.10.0`。功能与全部用例为 **planned**，未执行产品 E2E，无 PASS 证据和发布资格。以下是待实现用例规格；步骤具体描述目标行为，缺少的程序和环境逐项列明。不能把文档完整误报为用例可执行。

## 共用前置与执行规则

依赖功能：`TM-001`、`TM-007`。进入实现前按 [SOP-006](../../../sop/SOP-006-test-plan.md) 确定当轮版本/平台矩阵，按 [SOP-010](../../../sop/SOP-010-test-data.md) 建立数据、SQL、独立 expected 及重置程序，再按 [SOP-011](../../../sop/SOP-011-test-implementation.md) 绑定真实测试；执行遵循 [SOP-014](../../../sop/SOP-014-e2e.md)。账号只用合成测试用户，所有数据库、日志、授权和设置均隔离；不得用用户生产库造数。

下面给出的规划数字用于约束独立预期，并不声称已经生成对应厂商日志。原始格式、UI标识、测试函数和SQL尚未确定的部分，必须在该功能开发前补齐；不得发明当前不存在的执行命令。未来版本的测试平台以当轮设计为准，当前v0.1.0只声明macOS15 arm64/Intel。

## E2E-TM010-001 · 稳定版发现更新与数据保留

**验收：** `AC-TM010-001`，更新设置和说明可用；真实安装替换/重启成功，账号设置和统计保留，版本与包摘要一致。

**前置/数据：** 数据集 `update_packages`；依赖TM-001/007；update_packages planned。需真实已分发稳定版、候选最终包及相同分发profile的签名/清单；旧版有账号设置、手动地址、统计/队列独立快照。首版无历史稳定版时使用SOP017规定的候选→受控高版，不伪称稳定升级。

**步骤：**

1. 在隔离Mac安装真实旧稳定包，生成旧版数据并保存独立行数、金额、Token及设置快照。
2. 从App设置更新检查频率，重启确认保存，访问同机或已配置的可信源发现候选。
3. 查看版本说明，核对与候选release_id/Changelog一致；点击更新并等待下载与安装重启。
4. 不手工启动新App，检查新版本/包摘要、账号身份、设置、统计和队列，再完成同步。

**独立预期：** 更新频率和说明可用；只有声明候选被安装，Sparkle自主重启；更新前后账号/设置/统计与快照一致，队列不丢失不重复。完整更新体验仍为未来功能，TM-001-004通过只证明最小更新路径。

**绑定/证据/状态：** `planned`；`automated_test=null`，未有原生函数绑定和执行证据。按 SOP-010/011 补齐后由 SOP-014 执行；缺项：缺真实稳定版/候选fixture、频率与说明UI、旧版统计/SQL及包级原生绑定；不得引用受控build101为已分发稳定版。 预期证据包括当前release_id/候选SHA、输入与expected摘要、原始原生结果、逐步断言/必要截图、数据/故障恢复与清理记录；当前这些产品证据尚不存在。

## E2E-TM010-002 · 签名、网络、空间和迁移失败恢复

**验收：** `AC-TM010-002`，拒绝无效包，不进入半更新状态，恢复流程可自动验证。

**前置/数据：** 数据集 `update_packages`；对同一干净旧版分别建立四个隔离子场景：坏签名包、下载中断、受限测试卷空间不足、受控迁移失败；每个保存旧版包/DB/配置摘要。故障不能作用用户系统盘/生产库。

**步骤：**

1. 坏签名场景从App检查/安装，确认拒绝且旧版仍可启动。
2. 下载中断场景在传输中切断测试源，恢复后按产品重试入口继续，核对完整包验签。
3. 在隔离小容量卷启动空间不足场景，核对明确错误和旧版可用，不使用填满用户磁盘的方式造故障。
4. 迁移场景注入已定义失败点，等待更新/迁移失败恢复，再启动并核对旧版数据库和应用状态。

**独立预期：** 每个失败均不能形成半更新；原账号/统计和包的可用状态可验证。网络恢复后的成功需要完整包校验；迁移失败恢复来源与摘要明确。四个子场景全部为本case必需，不能挑一项通过。

**绑定/证据/状态：** `planned`；`automated_test=null`，未有原生函数绑定和执行证据。按 SOP-010/011 补齐后由 SOP-014 执行；缺项：缺四种故障程序、受限卷与迁移快照/SQL、安全清理器和原生绑定；现有TM001坏签名不覆盖其余三项。 预期证据包括当前release_id/候选SHA、输入与expected摘要、原始原生结果、逐步断言/必要截图、数据/故障恢复与清理记录；当前这些产品证据尚不存在。

## E2E-TM010-003 · 升级默认地址和手动覆盖

**验收：** `AC-TM010-003`，生产服务器确定后，升级包的新 HTTPS 默认地址只用于未手动改过地址的安装；已有手动地址跨升级保留，认证会话仍按服务地址隔离。

**前置/数据：** 数据集 `server_default_migration`；server_default_migration planned；两套旧安装A从未设置地址、B已手动设置；候选内置一个届时确定且测试可访问的生产HTTPS默认地址。两源有独立账号/数据/会话，公钥不可随URL编辑。

**步骤：**

1. 准备A/B旧版并分别记录默认/手动配置来源、实际服务和origin token，不能只比较URL字符串。
2. 从两套App分别执行真实签名升级到同一候选，等待自主重启。
3. 检查A采用新内置HTTPS默认，B保持原手动URL；再重启各一次。
4. 核对每套服务实际收到的请求与账号身份，旧origin token不得泄露给新origin；从UI恢复默认后再检查按新版值生效。

**独立预期：** 只有无手动覆盖安装跟随新版默认；显式覆盖即使恰好等于旧默认也应按已经确定的配置来源规则处理。改变origin需重新服务认证，旧token不能跨源复用。

**绑定/证据/状态：** `planned`；`automated_test=null`，未有原生函数绑定和执行证据。按 SOP-010/011 补齐后由 SOP-014 执行；缺项：生产HTTPS地址尚未确定、旧/新签名包fixture、默认迁移状态生成/SQL和原生绑定缺失；本版127.0.0.1配置通过不证明未来迁移。 预期证据包括当前release_id/候选SHA、输入与expected摘要、原始原生结果、逐步断言/必要截图、数据/故障恢复与清理记录；当前这些产品证据尚不存在。
