# 测试策略与发布门禁

## 1. 当前状态与硬性规则

当前仓库处于产品开发前的基础建设阶段。测试规范、数据生成器或质量检查脚本通过，只能证明这些基础设施自身可用。原生 Mac App、真实服务端、产品 E2E 执行器和发布环境尚未建立时，产品验收状态为 **BLOCKED**，不得称为“E2E 通过”或发布可用产品。

每项功能在设计时必须同时定义以下交付项，并在完成验收前全部实现：

1. 可验证的需求和验收场景。
2. 测试用户、测试数据及确定性生成/重置程序。
3. Codex 可直接执行的 SOP，包含命令、预期结果、退出码、失败处理和清理步骤。
4. 操作真实产品的可执行 E2E，以及对应的执行证据。

每一次产品迭代、补丁、测试版和正式版发布的**应执行集合**为：本次目标功能/修复的全部场景，加上所有此前已交付功能的完整 E2E 回归。与本次版本无关的未来 `planned` 功能不加入集合；目标功能不能通过改成 `planned` 或移动版本号规避验证。新功能用例通过、单元测试通过、人工点验成功，均不能代替这个集合的完整回归。

Codex 负责自动编写功能和测试、运行数据程序与 E2E、读取机器结果、定位修复失败并重新回归。SOP 是自动执行的操作合同；发布判定由受保护的门禁程序产生，不能转交用户逐项点验或填写通过报告。

每次版本计划分配不可变的 `release_id`：`vMAJOR.MINOR.PATCH-YYYYMMDDTHHMMSSZ`，时间为 UTC 计划创建时间。需求、功能拆分、开发计划、测试计划、发布说明、Changelog 和 Git 发布均使用该标识，规则见[统一版本规范](../standards/versioning.md)。每次执行另有唯一 `run_id`，失败重跑不得覆盖旧记录或改变版本标识。

## 2. 从需求追踪到执行证据

每项功能使用稳定的 `TM-001` 形式编号；缺陷使用 `BUG-*` 编号；场景使用 `E2E-TM001-001` 形式编号，明确所属功能。维护以下关联，任何缺项均阻断验收：

| 项目 | 必须记录 |
| --- | --- |
| 需求 | 用户目标、权限、输入输出、成功条件和失败行为 |
| 场景 | 关联需求编号、前置条件、用户操作、可断言的结果 |
| 数据 | 生成器和数据集版本、固定种子/时钟、用户角色、预期聚合值 |
| 执行 | 真实 E2E 测试名称、执行入口、所需 macOS/架构/数据库环境 |
| 证据 | release_id、run_id、执行结果、提交 SHA、候选版本、构建摘要、环境和产物链接 |

需求文档从[功能模板](../templates/feature.md)创建；缺陷从[修复模板](../templates/bugfix.md)创建。将上述关联收录为机器可校验的用例清单，校验器检查双向覆盖。状态规则如下：

- `planned`：已记录需求、场景、期望、数据依赖及 SOP；可把未实现的测试绑定设为 `null`，规划中的数据集可把生成程序设为 `null`。数据集一旦为 `available`，即使功能仍在设计，也必须绑定真实生成程序。
- `in_progress`：进入功能实现前，所有场景的数据集必须 `available`，生成程序和真实测试入口必须已经存在并绑定。测试可以暴露尚未实现的行为，不能用空脚本代替测试。
- `implemented`：保留完整绑定，并由机器门禁取得应执行集合的通过证据后，才能宣称验收完成。

未来功能缺执行器不妨碍无关版本按自身集合验收；本次目标或此前已交付功能缺少执行器、数据或结果则保持 BLOCKED。基础清单检查只核对引用，不证明测试已经执行。

测试断言基于预先计算并审阅的期望值，不能调用生产聚合逻辑生成自己的答案。不得通过删除失败场景、降低断言、改写期望值或仅替换为 mock 使门禁变绿；需求变化须先更新需求和验收依据。

## 3. 产品 E2E 的边界

### 真实端到端链路

以原生 SwiftUI App 的 UI 自动化为入口，连接隔离的真实 FastAPI 服务及真实数据库。完整产品主流程从首次启动、预置账号登录和日志目录授权开始，经日志解析、本地 SQLite 落库、上传、服务端统计，最终断言成员/管理员界面及导出结果。各阶段验证本次应执行集合对应的真实链路：例如登录版本贯通原生登录 UI、服务端认证和数据库；尚未交付的日志或导出步骤不提前加入该版本门禁。

- 使用测试生成的本地日志，不调用付费大模型 API。
- 认证、权限、解析器、队列、网络协议和数据库必须使用待发布产品实现；不能用测试替身绕过主链路。
- 使用 macOS 原生 UI 自动化测试目标；HTTP 测试和命令行测试用于辅助定位，不能冒充桌面产品 E2E。
- 可使用测试目录和外部故障注入；内部测试入口仅允许出现在测试构建中，不能改变业务语义或进入正式产物。候选安装包必须再以独立 UI 测试进程验证，不能把测试构建的结果当作正式包结果。
- 每个场景必须断言用户可见结果以及关键持久化/同步结果。截图只是辅助证据。

### 必测功能组

| 功能组 | E2E 必须验证的行为 |
| --- | --- |
| 账号和权限 | 首次登录、改密、退出、停用、重置、设备解绑、成员数据隔离和管理员汇总 |
| 授权和数据源 | 选择目录、拒绝/撤销授权、目录失效、重新授权、暂停和恢复 |
| 日志采集 | Codex/Claude Code 已支持版本、未知模型、子代理、恢复/分支、累计值重置、重复事件、移动日志、半行写入、未知格式 |
| 用量统计 | 今天/昨天/近 7/15/30 天和自定义范围、跨日/月、团队时区、缺失历史、输入输出和缓存不重复计算 |
| 费用 | 已配置/未配置价格、价格生效时间、历史价格版本、缓存价格、币种分别汇总 |
| 同步和团队 | 断网、进程退出、服务端失败、重启补传、重复上传、多设备、项目归属和未归属 |
| 导出和提醒 | 当前筛选/权限一致、CSV 内容准确、预算阈值、同周期不重复提醒 |
| 数据与升级 | SQLite 升级、SQLite→MySQL 迁移、备份恢复、签名包安装、旧版升级和配置保留 |

这些是设计基线，不表示功能或测试已经实现。功能首次合入必须把对应场景加入回归清单；后续每个产品版本都保留此前已交付功能的全部场景，并加上本次目标场景。

### 数据、版本兼容与安全隔离

生成器必须能从空环境创建固定角色、设备、项目、日志、价格和故障数据，并输出数据清单及独立期望值。固定随机种子与参考时间；系统时间相关场景另外覆盖真实时区边界。不得使用员工的私有会话、生产账号或生产数据库。

规范化用量样例仅用于明确统计语义，不能证明供应商日志解析兼容。每个声称支持的 Codex/Claude Code 版本必须有标明来源、工具版本和字段语义的合成原始日志样例，经过解析器与完整产品链路验证。测试不得把规范化记录直接写入业务表并宣称日志采集已通过。

生成、重置和清理只允许作用于带测试环境标记的专用目录/数据库。程序必须校验目标并拒绝生产地址、用户真实日志目录和未标记的数据库。生产安装包不内置测试账号、通用测试密码或故障注入入口。

## 4. 门禁判定与证据

| 阶段 | 进入下一阶段的必要条件 |
| --- | --- |
| 功能设计 | 需求、场景、数据生成方案、SOP 和 E2E 实现任务齐全；规划状态可保留待实现项 |
| 开始实现 | 对应数据集可用，真实数据程序和测试入口已绑定；不要求尚未实现的功能已经通过 |
| 迭代合入 | 静态检查/必要单元与集成测试通过，应执行集合的 E2E 全部通过，覆盖映射完整 |
| 候选发布 | 对候选提交重建产物并完成应执行集合的全部 E2E，适用的迁移和安装升级验证通过 |
| 正式分发 | 发布包与已验证包摘要一致，签名/公证/更新签名通过，证据齐全，才能更新发布清单 |

最终证据绑定同一 `release_id`、提交、版本、构建包摘要、服务端产物摘要、测试清单与 fixture 摘要。记录执行器版本、macOS 版本、CPU 架构、数据库版本、开始结束时间、退出码和逐场景结果；保留原始测试结果包、诊断日志、必要截图和安装升级报告。测试后任何产品、测试、数据或发布配置变化都会使原证据失效，必须重新验证。

需求与计划、Changelog 等源文档先纳入候选提交；机器在该提交上执行验证，再于受版本控制源码之外生成版本验收凭证（passport），记录候选 SHA 和真实产物来源。不能把手写通过记录当作凭证，也不能将包含最终提交 SHA 的生成报告反复写回该提交。基础建设版本可以记录规范检查结果，但产品 E2E 未通过时不得生成产品 PASS 或发布 tag。

统一状态：

- **PASS**：全部必需场景和矩阵项完整执行，全部断言通过，证据与候选一致。
- **FAIL**：发生断言、崩溃、超时、迁移、签名或其他确定性失败。
- **BLOCKED**：缺执行器、缺环境/权限/数据/证据，发现跳过、xfail、隔离中的不稳定测试，或无法确认覆盖完整。

只允许 PASS 发布。重试只能帮助诊断；失败后重试成功不能覆盖原始失败。必须查明原因、修复并从干净环境重跑完整回归；同一候选存在未解释的不稳定结果时保持 BLOCKED。不得使用 `continue-on-error`、空测试成功、伪造报告或手工填写 PASS 绕过门禁。

### macOS 与数据库验证矩阵

首版默认支持 macOS 14 及以上，并交付 Apple Silicon/Intel 通用包。发布前在兼容性清单中明确实际支持的 macOS 主版本和每个版本的构建号；凡已对外声明支持的“系统主版本 × 架构”组合都必须提供可运行环境和结果，操作系统本身不支持的组合需有事实依据。

- 每个支持组合都运行本次应执行集合的全部产品 E2E，以及实际签名安装包的安装、启动和升级验证。
- 开发兼容回归使用 SQLite，生产发布使用目标 MySQL 版本，分别验证本次应执行集合的真实业务链路；MySQL 可用跨矩阵共享服务环境，但每次测试数据必须隔离。
- 升级覆盖上一公开稳定版至候选版；存在更早仍受支持的直升路径时也逐一验证。首个没有上一稳定版的发布明确记录基线不存在，升级项只验证全新安装；从第二个发布开始必须自动获取上一稳定包并验证升级。
- 专用 Mac 或可运行桌面的 Mac 虚拟机必须具备已登录会话、Xcode、签名/公证权限和 UI 自动化所需授权。系统目录授权、通知、安装与更新对话框通过 UI 自动化执行并自动断言；尚不能自动执行的必需步骤保持 BLOCKED，不能改为人工勾选通过。

仓库中的检查脚本不能自行证明远端分支保护和发布权限已经配置。必须保存远端必需检查、禁止管理员绕过和发布凭据绑定受保护任务的配置证据；未配置时明确显示 BLOCKED。正式发布任务只能消费已通过门禁的候选产物，不能重新生成未被验证的安装包。

## 5. 缺陷与职责

修复缺陷时先建立可复现数据与回归场景，在未修复实现上取得失败证据，再修复并运行受影响检查和本次应执行集合的全部 E2E。无法取得可靠复现时先补诊断和记录，不能把“暂时没有出现”视为修复完成。

负责实现的 agent 同时负责测试、数据程序和 SOP；审查 agent 对需求覆盖、独立预期值、证据绑定和门禁绕过风险进行检查。账户授权、证书和测试机器初始化可能需要外部管理员预先提供；缺少这些前提时必须指出具体缺项，不能声称已经自动验证。人工审核不能替代缺失的自动化测试或解除 BLOCKED。
